## Overview

Phase 1 gave the MCP server the interview: `eligian_brief` hands out rounds and records answers in `BRIEF.md`, and `confirm` records a confirmation the agent reports. Nothing was enforced. Phase 2 makes the brief binding before generation and adds the paths around it:

- **The record of known programs** (`cli/mcp/brief/known-programs.ts`): `.eligian/programs.json` in the project. The first run in a project records every existing program as known. After that a program becomes known only through an approved brief, an approved addition, or the user accepting it (`accept-existing`). The record is on disk, so it survives a server restart (roadmap §4.2, decision 12; `spikes.md` §5 item 1). The server writes it, with one narrow exception: the CLI's `eligian init` writes the first record of the project it creates (FR-060).
- **The gate** (`cli/mcp/brief/gate.ts`): `eligian_init` (every starter, `library` included), `eligian_check`, `eligian_fmt`, `eligian_compile` and `eligian_smoke` refuse a program file per the table of §4.2. A refusal is a new tool failure kind, `gate`, that carries the code, the brief's state and the next round.
- **Sign-off** (`cli/mcp/brief/signature.ts`): `confirm` and a new `approve-storyboard` ask the user by elicitation, with a time limit, telling accepted, declined, cancelled and no answer apart. The agent-reported fallback stays. The confirmation and approval lines carry an HMAC made with a per-user key outside the project (§5.3), replacing Phase 1's plain SHA-256 digest.
- **Additions** (§4.3): a new timeline, a new language or a first `extensions` block in an existing presentation is refused with `addition-not-briefed` and a scoped round. `eligian_brief` with `scope: { addition, name }` runs that short interview into an `## Addition` section of `BRIEF.md`.
- **Adoption** (`cli/mcp/brief/adopt.ts`, §4.4): `scope: 'adopt'` reconstructs a brief from an existing program. What the code settles is recorded as facts; the frontier is what the code does not settle; conflicts between a fact and an answer are reported.
- **The CLI warning** (§4.5): `eligian check`, `compile`, `smoke`, `fmt` and `dev` print one stderr line for a program whose brief is not approved, or that is not in the record. Exit codes and stdout do not change.
- **`eligian_project`'s `brief` section** and the **brief state on each telemetry line**.

Exit (roadmap §8 Phase 2, verbatim): "the gate-matrix spec is green; in Claude Code, a new presentation cannot pass `eligian_check` before both sign-offs, and an existing example project works unchanged; adding a timeline to it is refused until its scoped interview is approved; `scope: adopt` on the eligian-tour example yields a brief whose views, providers and languages are facts and whose frontier holds only undecided questions; `eligian check` on a program with an unapproved brief prints the warning and exits as before." Each clause is a success criterion below: the gate matrix SC-001; the three "in Claude Code" clauses (a new presentation, the existing example unchanged, the added timeline refused until its scoped interview is approved) are all steps of the one real-client run SC-013, with in-process stand-ins in SC-001 and SC-008 so CI covers the logic; adoption SC-009; the CLI warning SC-010.

## User scenarios and testing

### User story 1: a new presentation cannot be generated before both sign-offs (P1)

**Acceptance scenarios**:
1. **Given** an empty project, **When** the agent calls `eligian_init` (template `blank`) or writes `talk/main.eligian` with its editor and calls `eligian_check`, **Then** the call fails with kind `gate`, code `brief-required`, and the first round of an empty brief.
2. **Given** a `BRIEF.md` in `talk/` whose frontier is not empty, **When** `eligian_check` runs on `talk/main.eligian`, **Then** it fails `brief-incomplete` with the brief's next round.
3. **Given** a complete brief, **When** the agent calls `confirm` in a client that announces elicitation, **Then** the user sees a dialog with the counts, the delegated answers and the `BRIEF.md` path, and one checkbox; ticking it confirms the brief with mode `elicitation`.
4. **Given** a confirmed brief and a `STORYBOARD.md`, **When** the agent calls `approve-storyboard`, **Then** the storyboard is checked against the brief, the user approves it, and `eligian_check` on the program runs.

### User story 2: existing work runs as today (P1)

**Acceptance scenarios**:
1. **Given** a copy of `examples/eligian-tour/` and no `.eligian/programs.json`, **When** the server starts there, **Then** `tour.eligian` is recorded as known and `eligian_check`, `eligian_compile`, `eligian_fmt` and `eligian_smoke` on it return what they return without Phase 2.
2. **Given** that project, **When** the server restarts (a new session, or every turn of a headless run), **Then** `tour.eligian` is still known and a program the agent wrote after the first start is not.
3. **Given** a program that arrived by `git pull`, **When** the user accepts it through `accept-existing`, **Then** it is known.
4. **Given** a colleague's clone of an approved, built presentation (its signed `BRIEF.md` committed, no `.eligian/`), **When** the server starts there and `eligian_check` runs on the program, **Then** it runs: the first-run scan records it, and a known program is existing work whatever its brief's state or signature (§5.3, FR-012 row 4).
5. **Given** an empty directory, **When** the user runs `eligian init --template blank` there and an agent's server starts in it, **Then** `.eligian/programs.json` already exists (written by `eligian init`, without the `main.eligian` it wrote), the server does not scan, and the first `eligian_check` on `main.eligian` fails `brief-required` (FR-060).
6. **Given** a known `first-run` program in a directory, **When** the agent starts a main brief there (`status` with an idea), **Then** the program still runs: a main brief started beside existing work gates nothing (FR-012 row 4).

### User story 3: an addition gets a short interview (P1)

**Acceptance scenarios**:
1. **Given** the known tour, **When** the agent adds `timeline "Outro" …` and calls `eligian_check`, **Then** it fails `addition-not-briefed` with the round for the view `Outro`.
2. **Given** that scoped interview confirmed and its storyboard section approved, **When** `eligian_check` runs, **Then** it runs, and `Outro` is in the record.
3. **Given** the known tour, **When** the agent changes copy, a beat, a class or an interaction inside an existing view, **Then** nothing is refused (decision 7).

### User story 4: an existing presentation is given a brief (P2)

**Acceptance scenarios**:
1. **Given** a copy of the tour, **When** the agent calls `eligian_brief` with `scope: 'adopt'`, **Then** `BRIEF.md` records the 9 views, their providers, the two languages, the entry view, the navigation, the keys and the host module as facts (`by: code`), and the round asks only questions the code does not settle.
2. **Given** C3 answered without `keyboard`, **When** the reply is built, **Then** it reports the conflict with the keys the code wires (I2).
3. **Given** an adopted brief that is not yet approved, **When** `eligian_check` runs on the tour, **Then** it runs: adoption never closes the gate on existing work.

### User story 5: the terminal stays usable (P2)

**Acceptance scenarios**:
1. **Given** a program whose `BRIEF.md` is open, **When** `eligian check main.eligian --format json` runs, **Then** stderr has one warning line, stdout is byte-identical to the run without `BRIEF.md`, and the exit code is the same.

## Requirements

### Functional requirements

#### The record of known programs (`brief/known-programs.ts`)

- **FR-001** **The file.** The record is `<project root>/.eligian/programs.json` (§4.2, decision 12). The directory is created with `ensureEligianDir` (`cli/dev/runtime-reports.ts:228`), so it gets its self-ignoring `.gitignore` (`*`) when it is created and an existing one is left alone. The file is UTF-8 JSON, 2-space indented, LF, ending in one LF:
  ```json
  { "version": 1, "programs": [ { "path": "talk/main.eligian", "timelines": ["Intro"], "languages": ["en-US"], "extensions": false, "via": "first-run" } ] }
  ```
  - `path`: relative to the project root, forward slashes; entries sorted by `path` (code-unit order).
  - `timelines`: the timeline names in source order; `languages`: the codes of the `languages` block in source order (empty when there is none); `extensions`: whether the program has an `extensions` block (§4.2 "its timeline names, its languages and whether it has an `extensions` block").
  - `via`: `first-run` (the server's scan, FR-003, or the CLI's `eligian init`, FR-060), `brief` (FR-031, and the program `eligian_init` writes under an approved brief, FR-061), `addition` (FR-040), `accepted` (FR-009) or `adopted` (FR-049). There is no `starter` value. For `accepted`, a `mode` field (`elicitation` or `agent-reported`) as for the sign-off (FR-020).
  - Writes go through `writeFileAtomic` (`cli/atomic-write.ts:39`) with the changed-file check of its `beforeRename` (FR-007).
- **FR-002** **The text scan.** `scanProgram(source: string): { library: boolean; timelines: string[]; languages: string[]; extensions: boolean }` reads a program without the compiler (§4.2 "a text scan, no compiler"). Comments are ignored; text inside string literals is never taken for a keyword or a comment (a `"https://…"` URL is not a line comment). `library` is computed by the same string-aware tokenizer: the first token after comments is the keyword `library`. That differs from `isLibrary` (`cli/check/check-command.ts:52–55`, which strips `/* */` and then `//` with plain regexes, not string-aware) only on contrived input where a comment marker inside a string hides or reveals the `library` keyword; on every program in the repo the two agree, and where they differ the scan follows the parser (SC-003). `isLibrary` itself is not changed.
  - **Imports.** `check-command.ts` imports `@eligian/language` directly (`:14–19`), `../compile-file.js` (`:22`) and `./lint.js` (`:23`), so importing `isLibrary` or `expandPatterns` from it loads the language package. Both functions (and `toGlobPath`) move unchanged into a new module `cli/check/files.ts` that imports only `node:fs`, `node:path` and `tinyglobby`; `check-command.ts` re-exports them, so its six importers (`fmt.ts:13`, `mcp/paths.ts:16`, `mcp/tools/compile.ts:31`, `project.ts:44`, `smoke.ts:25`, `smoke/smoke-command.ts:18`) are unchanged. `known-programs.ts` (the scan, the record, `findRecordFile`) and the CLI warning path (FR-053) import from `cli/check/files.ts`, `node:*` and `signature.ts` only, never from `@eligian/language` (checked by a grep test, SC-003). Two more importers change so that the gate, the CLI warning and `verifyBriefFile` load no language code (plan readings P1, P2; plan-review ruling): `mcp/paths.ts` imports `expandPatterns` from `cli/check/files.ts` instead of `check-command.ts`, and `brief/references.ts` checks language codes with a local copy of the language-code pattern instead of importing `isValidLanguageCode`, with a drift test that compares the two on the language package's own cases.
  - The scan is pure and synchronous and never throws (an unreadable construct yields what was read before it). Its results equal the parser's on every program in the repo (SC-003).
- **FR-003** **The first-run scan.** When a project root has no record, the server scans it (FR-062 lists where the start-time scan is skipped): every `.eligian` file that `expandPatterns(['.'], root)` returns (`cli/check/check-command.ts:73`, moved to `cli/check/files.ts` by FR-002; `node_modules` skipped) and whose scan is not a library is recorded with `via: first-run` (§4.2 "The first time the server runs in a project there is no record. It scans the project for `.eligian` files and records them all as known"). The scan of the server's working directory starts at process start (except where FR-062 says it does not), in `makeServerLayer` (`cli/mcp/server.ts:71`), before `initialize` is answered but without delaying it: it runs in the background and every gated call and every `eligian_brief` call waits for it (§4.2 "The scan covers the server's working directory at process start"; `spikes.md` §2, "the first tool call arrived 7.6 s after the process started"). `ServerOptions.brief.beforeScan?: () => Promise<void>` is awaited at the start of the scan, so a test can hold the scan open (SC-015); it cannot change what the scan records. A project that `eligian init` created already has a record (FR-060), so the server finds it and does not scan.
- **FR-004** **An announced root outside the working directory.** When a call's project root (`projectRoot`, `cli/mcp/paths.ts:63`) is not the working directory and has no record, that root is scanned at that call, before its gate. The same holds for the first announced root of a server that skipped its start-time scan (FR-062) (§4.2 "When the first tool call shows an announced root outside it, that root is scanned then"). Only the first announced root is a project (`paths.ts` reads `roots[0]`; `spikes.md` §2 "the others must not be scanned").
- **FR-005** **Read on every call, never rescanned once seen.** The record is read from disk on every gated call and every `eligian_brief` call; nothing about it is cached across calls (Phase 1 edge case "Stale caches"). Once one server process has read or written a root's record, a later absence of the file (deleted by hand or by the agent) does not trigger a new first-run scan: that process treats the record as its last copy and writes that copy back on its next record write. Only a root this process has never seen a record for is scanned (§9 risk 3 "only the first run in a project accepts what is there").
- **FR-006** **A record that does not parse** (invalid JSON, wrong `version`, wrong field types) is treated as a record with no programs. It is not rescanned and not overwritten until a write replaces it (`accept-existing`, an approval). Every gate refusal made under it names the problem in its `message`. A record that cannot be read for another reason (EACCES, a directory) fails the call with kind `io` through `toToolError` (`cli/mcp/errors.ts:76`).
- **FR-007** **Concurrent writers.** Within one server, record writes run one at a time under one semaphore per root (the pattern of `makeBriefLocks`, `cli/mcp/tools/brief.ts:175`). Across processes, each write re-reads the file before the rename; when it changed, the write merges again (union by `path`; for the entries this call writes, its values win) and retries, at most 5 times, then fails with kind `io` "programs.json changed while writing; call again" and leaves the other writer's version on disk. `ServerOptions.brief.recordBeforeRename?: (target: string) => Promise<void>` is awaited before each re-read, as Phase 1's `beforeRename` (`cli/mcp/tools/brief.ts:166`), so a test can change the file between the read and the rename (SC-002).
- **FR-008** **Who writes the record.** The MCP server writes it: the first-run scan (FR-003), `accept-existing` (FR-009), the approval of a brief (FR-031), of an addition (FR-040) and of an adopted brief (FR-049), and `eligian_init` under an approved brief (FR-061). The CLI never writes it and never creates `.eligian/` for it, with exactly one exception: `eligian init` writes the project's first record (FR-060). `check`, `compile`, `smoke`, `fmt`, `dev` and the CLI warning only read it (§4.5, amended by the user's ruling in `roadmap.md` §4.5).
- **FR-009** **`accept-existing`.** `eligian_brief` with `action: 'accept-existing'` and `paths` (files, directories and globs under the root, resolved with `resolveInputPatterns`, `cli/mcp/paths.ts:106`) takes in programs that arrived without the agent (§4.2 "Accepting existing work").
  - Library files among the matches are skipped and listed as such.
  - The user is asked as in §5.1 (FR-020): the dialog lists each program with its timelines, languages and whether it has an `extensions` block. The sign-off is bound to the sorted paths and to each program's scan (FR-020 ticket, FR-063): when a program's scan differs after the dialog, nothing is written and the call fails `io` "a program changed while asking; call again" (copy edits that leave the scan equal do not invalidate it).
  - It covers exactly the roadmap's two cases (§4.2): a program **not yet in the record** (the user wrote it by hand, or `git pull` brought it), and a **renamed timeline** in a known program ("A renamed timeline shows as a new one; the same action covers it"). For a known program, the current scan is compared with its entry plus the approved additions of its directory (FR-032): it is a rename when every new timeline name is matched by a recorded name that disappeared (the number of new names is at most the number of removed names), no language code is new and no `extensions` block is new. Anything else is an addition (§4.3, decisions 2 and 7), which needs its scoped interview: the call is refused with `addition-not-briefed`, writes nothing, and carries `scope` and `round` of the first addition as the gate does (FR-034), so the agent goes to the scoped interview (FR-037). A known program whose scan equals its entry is listed as unchanged and not rewritten.
  - On acceptance, each accepted program's entry is written with its current scan and `via: accepted`, replacing an older entry for the same path.
  - A program governed by a `BRIEF.md` (FR-011) is refused with `governed-by-brief` and is not written: its brief decides.
  - When one matched program is refused (`addition-not-briefed`, `governed-by-brief`), the whole call is refused before the user is asked, as the gate refuses a whole call (FR-010, R-12); libraries are skipped, not refused.

#### Governance and the gate (`brief/gate.ts`)

- **FR-010** **What is gated.** The gate is evaluated per program file: a `.eligian` file that is not a library (§4.2 "a file with a timeline; `library` files are not presentations and are not gated"). `eligian_check`, `eligian_fmt` and `eligian_smoke` gate every program file their `paths` match; `eligian_compile` gates its `path`. When any matched program is refused, the whole call fails and runs nothing; the failure lists every refused program (FR-016). `eligian_docs`, `eligian_operations`, `eligian_project` and `eligian_brief` are never gated (§4.2).
- **FR-011** **Which brief governs a program.** A program is governed by the `BRIEF.md` in its own directory (the brief's directory is where its R3 entry file lives, Phase 1 FR-013), when that file holds a **main brief**: an idea, an answer outside the addition sections, or a confirmation line. A `BRIEF.md` that holds only addition sections (FR-035) governs nothing; its additions apply to the known programs of its directory. An adopted brief (FR-041) governs nothing until it is approved (§4.4 "until the adopted brief is approved, the program stays existing work under §4.2"). On Windows the file is matched case-insensitively, as the file system does.
- **FR-012** **The matrix** (§4.2, the table, plus the two rules of §5.3 and §1/decision 10 that the table leaves implicit; the first row that matches decides):

  | # | Situation | Verdict |
  | --- | --- | --- |
  | 1 | Not governed, known (in the record) | runs, unless it contains an addition (FR-034) |
  | 2 | Not governed, not known | refused `brief-required`; the reply names `accept-existing` for work that did not come from the agent |
  | 3 | Governed, known, its entry's `via` is `brief`, `addition` or `adopted` (its brief was approved once) | runs, unless it contains an addition (FR-034), whatever later edits (through the tool or by hand) did to the brief's answers or signature (§1 non-goals "The brief does not stay binding after approval … Only additions need a new interview"; decision 10) |
  | 4 | Governed, known, its entry's `via` is `first-run` or `accepted`, whatever its brief's state (`open`, `complete`, `confirmed`, `approved`; a confirmation that does not verify; changed answers) | runs, unless it contains an addition (FR-034): existing work, also beside a main brief started later (§4.2 decision 2; §5.3 "A project that already has its program is existing work under §4.2 and is not affected") |
  | 5 | Governed, frontier not empty | refused `brief-incomplete` |
  | 6 | Governed, the answers changed after a confirmation (FR-026) | refused `brief-changed`; the reply lists only the changed answers |
  | 7 | Governed, frontier empty, no valid confirmation | refused `brief-not-confirmed` |
  | 8 | Governed, confirmed, no valid approval | refused `storyboard-not-approved` |
  | 9 | Governed, approved | runs, unless it contains an addition (FR-034) |

  Rows 3 and 4 together cover every known governed program (every `via`): rows 5 to 9 decide only a program that is not in the record. A main brief started beside existing work (`status` with an idea in a directory that holds a known `first-run` or `accepted` program) creates a governing brief that never gates that program; only its additions are refused. Rows 3 and 4 apply only to a program that exists and is in the record. A program the agent is about to write (`eligian_init`'s target, FR-013) or wrote after the record was made is not known, so rows 5 to 8 decide it: a brief confirmed on another machine "with no program written yet, is asked to be confirmed again (one dialog)" (§5.3). In rows 3 and 4 the approved set for the addition check is the program's record entry plus the approved additions of its directory (FR-032), not the brief's current answers, so editing S2 after approval does not add a view without its interview. `BRIEF.md` stays hand-editable after approval: no gate, tool call or approval refuses or rewrites such an edit (FR-026).

  The verdict is a pure function `gateVerdict(input): Verdict` of the program's scan, its record entry, the governing brief's evaluation and signature status, and the approved additions; it does no I/O, so the whole matrix is tested without a server (SC-001).
- **FR-013** **`eligian_init`** follows the matrix for its target directory with every starter, `library` included: the program it would write is `<directory>/main.eligian` (`STARTER_ENTRY`, `packages/language/src/starters/starters.ts:31`), governed by `<directory>/BRIEF.md` (§4.2 "`eligian_init` follows the same table for its target directory"). With no governing brief it runs only when that program already exists and is known (re-initialising existing work with `force`).
  - **The `library` starter is gated like the others.** It writes a program (`main.eligian` with `timeline "${title}" … using raf` beside the library, `starters.ts:489–512`), so the program it would write is refused `brief-required` (or by rows 5 to 8) like any other starter's. Roadmap §4.2's exemption is removed (done in `roadmap.md`). No `via` value exists for it (FR-001).
  - What `eligian_init` records after it writes under an approved brief is FR-061.
- **FR-014** **Order inside a call.** The gate runs after the paths resolve and before anything else: before the compiler lock is taken, before a document is loaded, before `eligian smoke` is spawned and before `eligian_init` writes a file. A refused call writes nothing and takes no lock. The gate reads `BRIEF.md` without the brief's permit (an atomic rename means a read sees one whole version). A program the gate reads is a tool input: a missing one fails `not-found` naming the file, any other read failure `io`, so spec 058's missing-path contracts hold (build ruling, T028).
- **FR-015** **The gate never writes.** A refusal does not create `BRIEF.md`, an addition section or a record entry. The next round it carries is computed from the file as it is (for `brief-required`, from an empty brief; for `addition-not-briefed`, from the addition's scoped tree, FR-036).

#### The `gate` failure (`errors.ts`)

- **FR-016** **The new kind.** `ToolErrorKind` (`cli/mcp/errors.ts:12`) gains `gate`, and `ToolError` (`:29`) gains `ToolGateRefused`, a `Data.TaggedError('ToolGateRefused')` with `{ message; path?; gate: GateRefusal }`. `toToolFailure` (`:50`) maps it to `{ header, error: { kind: 'gate', message, path?, gate } }`, and the `ToolFailure` schema (`:34`) gains the optional `gate` field. The other kinds and their mapping are unchanged (§4.2 "A refusal is a tool failure of a new kind, `gate` (today's kinds are `not-found`, `io`, `timeout`, `cancelled`, `internal`)").
- **FR-017** **The payload** (§4.2 "It carries the code, the brief's state and the next round, so one refused call gives the agent everything it needs to continue the interview"). `GateRefusal`:
  - `code`: `brief-required`, `brief-incomplete`, `brief-not-confirmed`, `storyboard-not-approved`, `brief-changed` or `addition-not-briefed`
  - `program`: the absolute path of the first refused program; `refused`: every refused program with its code (FR-010)
  - `brief`: the absolute path of the governing (or would-be) `BRIEF.md`; `directory`: the value to pass as `eligian_brief`'s `directory`
  - `state`: the brief's state (`none` when there is no `BRIEF.md`)
  - `round`: the next round, as `eligian_brief` returns it (Phase 1 FR-030 items)
  - `scope`: for `addition-not-briefed`, the `scope` value to pass (`{ addition, name }`), and `additions`: every trigger found (FR-034)
  - `changed`: for `brief-changed`, the changed answers (FR-026)
  - `next`: one instruction, for example for `brief-required`: "Ask the user for their idea and call `eligian_brief` with `action: status`, `directory: <dir>` and the idea verbatim. If this program did not come from you, ask the user and call `eligian_brief` with `action: accept-existing`."

  The `message` is one line naming the code and the program. The header is the tool's own (`failureHeader`, `cli/mcp/server.ts:63`). The result has `isError: true`, as every declared failure.

#### Sign-off (`brief/signature.ts`, `tools/brief.ts`)

- **FR-018** **When the server elicits.** The server elicits only when the client announced form elicitation: `McpServerClient.clientCapabilities.elicitation !== undefined`, read with `Effect.serviceOption(ai.McpSchema.McpServerClient)` as `projectRoot` reads the roots capability (`cli/mcp/paths.ts:65–68`; `spikes.md` §1.1, the measured capability `{ "elicitation": { "form": {}, "url": {} } }`). The request is `ai.McpServer.elicit({ message, schema })` (effect 4.1.4 `ai/McpServer.d.ts:1296`, `@stability unstable`; roadmap §9 risk 6). Elicitation is used for three sign-offs only: `confirm`, `approve-storyboard` and `accept-existing` (§2 item 2; §4.2 "asks the user to confirm (as in §5.1)").
- **FR-019** **The forms use boolean and string fields only** (§2 "The sign-off forms therefore use only boolean and string fields"; `spikes.md` §1.3, Codex). Each form has exactly one required boolean: `confirmed` for `confirm` ("This brief is complete and correct", §5.1), `approved` for `approve-storyboard`, `accepted` for `accept-existing`. The `message` carries the summary as text:
  - `confirm`: the counts, the delegated answers with the agent's choices, the conflicts (FR-046), the absolute `BRIEF.md` path; on a re-confirmation after `brief-changed`, only the changed answers with their new values, and no counts, delegated answers or conflicts (§4.2 "re-confirming shows only the changed answers"; old values are not shown, since `BRIEF.md` keeps none: compliance ruling, 2026-11-20)
  - `approve-storyboard`: the absolute `STORYBOARD.md` path and its counts (views, beats, interactions)
  - `accept-existing`: the programs with their timelines, languages and `extensions` flag
- **FR-020** **Four outcomes** (§2, §5.1; `spikes.md` §1.2, §4.2, §5 item 3):
  - **accepted** with the boolean `true`: signed with mode `elicitation`.
  - **declined**: the `elicit` effect fails with `ElicitationDeclined` (`ai/McpSchema.d.ts:3890`), or the form is accepted with the boolean `false`. Nothing is written. The reply has `refused: { code: 'declined' }`, and `next` tells the agent to ask the user what to change. A `confirmation` passed in the same call is ignored (a decline is the user's no; `spikes.md` §5 item 3 "a decline (the user said no) does not" fall back).
  - **cancelled**: the effect's exit has an interrupt-only cause (`Cause.hasInterruptsOnly`; `spikes.md` §1.2 "a cancel … is an interruption of the effect", §4.2 "cancelled 12 ms after it was sent").
  - **no answer**: no outcome within the time limit (FR-021).
  - Two edge outcomes (plan reading P6, plan-review ruling): a client that answers the elicitation with a JSON-RPC error (an `ElicitationDeclined` that carries a cause, `McpServer.js:2624`) counts as **cancelled**; a form accepted with content that does not decode counts as **declined**.

  For cancelled and no answer, no one could be asked, and §5.1's two steps apply in order ("the server says so in its reply, and the agent uses the fallback below"):
  1. **That call writes nothing**, whatever it carries: a `confirmation` passed in the same call is ignored, because the user has not yet seen the summary. The reply has `refused: { code: 'elicitation-unavailable', outcome: 'cancelled' | 'no-answer' }`, `summary` (the dialog's `message` text, FR-019) and `ticket`, and `next` tells the agent to show the user the summary in the conversation and call again with their reply verbatim as `confirmation` and the `ticket`.
  2. **A later call** with a non-blank `confirmation` and that `ticket` is signed with mode `agent-reported`, the message recorded verbatim (the §5.1 fallback), without eliciting again. The `ticket` is `hmac-sha256:<64 hex>` with the key (FR-023) over the canonical JSON of `["eligian-signoff-ticket/1", action, section, sha256 of the BRIEF.md bytes or null, sha256 of the STORYBOARD.md bytes or null, the sorted accepted paths or null, the scans of those programs or null]`. For `accept-existing`, `section` is `accept-existing`, the `BRIEF.md` hash is `null` (its paths may span directories with no brief), and the last two elements are the sorted paths and, in that order, each program's scan as `[timelines, languages, extensions]`; for the other actions both are `null`. It needs no server memory, so it survives the restart of every headless turn (`spikes.md` §4.1), and it binds the confirmation to the files the summary was made from (for `accept-existing`: to the paths and the scans, so a program whose scan changed since the summary invalidates it): when it does not verify (another file version, another key, typed by hand, another scan), the call is handled as a first call (step 1, eliciting again where the client announced elicitation). The server creates the key for the ticket if it does not exist (FR-023).

  A client without elicitation goes straight to step 2 without a ticket, as in Phase 1 (the agent shows the summary that `status` or the refused call gave); there, a missing or blank `confirmation` is `confirmation-missing` (Phase 1 FR-029).
- **FR-021** **The time limit.** Every elicitation is bounded by `Effect.timeoutOption` (the spike's pattern, `specs/059-presentation-assistant/spikes/brief-spike-server.ts:77–83`). The default is 300 s (reading R-2). `ServerOptions.brief.elicitationTimeoutMs` overrides it for tests.
- **FR-022** **No permit is held while the user decides.** The elicitation runs outside the brief's permit and outside Phase 1's uninterruptible section (`cli/mcp/tools/brief.ts:396–398`), so other calls on the same brief, and the client's cancellation of the tool call, are not blocked by an open dialog. After the outcome, the call takes the permit, re-reads `BRIEF.md` (and, for `approve-storyboard`, `STORYBOARD.md`), and signs only when both are byte-identical to what the dialog summarised. Otherwise it writes nothing and fails with kind `io`: "BRIEF.md changed while asking; call again" (or `STORYBOARD.md`). For `accept-existing` the check after the dialog is FR-063 instead.
- **FR-023** **The key** (§5.3 "an HMAC over the answers, made with a key in the user's state directory, outside the project"). The state directory is `ServerOptions.brief.stateDir`, else `ELIGIAN_STATE_DIR` (§7.1), else the platform default: `%LOCALAPPDATA%\eligian` on Windows (`<home>\AppData\Local\eligian` when unset), `~/Library/Application Support/eligian` on macOS, `$XDG_STATE_HOME/eligian` or `~/.local/state/eligian` elsewhere (reading R-3). The key file is `<state dir>/brief-key`: 32 random bytes (`node:crypto`), hex, one LF. It is created on first need with the exclusive flag (`wx`) and mode `0o600`; on `EEXIST` the existing key is read, so two servers starting together end with one key. The CLI and the gate only read it (FR-008); when it does not exist, no signature verifies.
- **FR-024** **The signed lines** replace Phase 1's header lines (Phase 1 FR-019 item 4; `brief-file.ts:103–104`, `:577–587`):
  - `- confirmation: none`, or `- confirmation: <elicitation|agent-reported> <ISO-8601 UTC> round <n> hmac-sha256:<64 hex>`, where `n` is the highest `round` or `reviewed` among the recorded answers at signing (the watermark of FR-026)
  - `- confirmation-message: <JSON string>`, only for `agent-reported`
  - `- approval: none`, or `- approval: <elicitation|agent-reported|existing-storyboard> <ISO-8601 UTC> hmac-sha256:<64 hex>`
  - `- approval-message: <JSON string>`, only for `agent-reported`

  The HMAC-SHA256 (`node:crypto` `createHmac`) is over the canonical JSON of `["eligian-brief/1", kind, section, mode, at, n, answers]` where `kind` is `confirmation` or `approval`, `section` is `brief` or the addition's heading (FR-035), and `answers` is Phase 1's FR-022 canonical list (`[id, value, by]` of the recorded, non-dormant answers to applicable questions, sorted by id; `digest`, `cli/mcp/brief/engine.ts:1040`, shows the canonical form). The approval's payload also holds the confirmation's HMAC, so an approval never outlives its confirmation. The mode is recorded on the line, so the weaker form is visible (§5.1; §9 risk 4).
- **FR-025** **Verification** is pure given the key: `verifyBrief(parsed, evaluation, key): { confirmation: 'none' | 'valid' | 'invalid'; approval: 'none' | 'valid' | 'invalid' }`. `verifyBriefFile(dir, stateDir)` reads `BRIEF.md` and the key and returns the same, without the server (the disk-only read that the Phase 3 hook needs, §6.3 "The hook reads only what is on disk"). A line whose HMAC does not verify (forged, typed by hand, made with another machine's key, or over answers that changed since) counts as not confirmed / not approved (§5.3). A Phase 1 `sha256:` line parses as an invalid confirmation.
- **FR-026** **The state** extends Phase 1 FR-023, computed on every call, never read from the `state:` line:
  - `approved`: the frontier is empty, the confirmation is valid and the approval is valid
  - `confirmed`: the frontier is empty and the confirmation is valid
  - `complete`: the frontier is empty and the confirmation is not valid
  - `open`: otherwise

  **Changed answers.** When a confirmation line is present but invalid, the answers whose `round` or `reviewed` is greater than its watermark `n` are the **changed** answers. With at least one, the gate's code is `brief-changed` (FR-012) and the reply's `changed` lists them (`{ id, title, value }`); with none (a hand edit, or another machine's key), the code is `brief-not-confirmed` and the whole brief is confirmed again in one dialog. §5.3 in full: "The key is per user and per machine. A brief confirmed on another machine, with no program written yet, is asked to be confirmed again (one dialog). A project that already has its program is existing work under §4.2 and is not affected." So these two codes apply only to a program that is not in the record (FR-012 rows 5 to 8); a known program is existing work whatever its brief's state or signature (FR-012 rows 3 and 4).

  **After approval.** `brief-changed` and `brief-not-confirmed` apply only until the brief is approved (§1 non-goals "The brief does not stay binding after approval"; decision 10 "After approval: the brief is a record of the starting decisions"; §1 "`BRIEF.md` is Markdown; the user edits it in any editor"). Once approved, its program is in the record with `via: brief` (FR-031) or `adopted` (FR-049) and runs unless it contains an addition (FR-012 row 3), whatever later edits (through the tool or by hand) do to the signature. `BRIEF.md` stays hand-editable after approval: neither the gate nor any tool call refuses, rewrites or flags such an edit as an error. The reply of `eligian_brief` still reports the computed state (for example `complete` with `changed`) and offers re-confirmation, which records the new answers but is not required for generation. After approval only additions are refused (FR-012 row 3, FR-034); this is the user's ruling of 2026-11-19 (R-4).
- **FR-027** **`confirm`** keeps Phase 1's refusals (`frontier-not-empty`, Phase 1 FR-029) and signs as FR-020 to FR-024 describe. Confirming a brief whose confirmation is valid is a no-op (Phase 1 FR-029). The Phase 1 specs and fixtures that pin a `sha256:` line change to the signed form; nothing else in Phase 1's behaviour changes.

#### `approve-storyboard` (§5.2)

- **FR-028** **The action.** `eligian_brief` with `action: 'approve-storyboard'` is refused with `brief-not-confirmed` until the brief is confirmed (§4.1 "`approve-storyboard` is refused until the brief is confirmed and `STORYBOARD.md` passes the checks in §5.2"), with `storyboard-missing` when `<directory>/STORYBOARD.md` does not exist (reading R-5: the storyboard lives next to `BRIEF.md`, where `eligian_project` reads it, `cli/mcp/tools/project.ts:443`), and with `storyboard-mismatch` and the list of `problems` when a check of FR-029 fails. A refusal is a successful result with `refused`, as Phase 1's (Phase 1 R-8). Once the checks pass, the user approves as in §5.1 (FR-018 to FR-022).
- **FR-029** **The checks**, each with its own problem code (§5.2, in its order):
  1. `storyboard-ignored-rows`: `readStoryboard` reports `ignoredRows > 0` (§5.2 "it parses, with no ignored rows").
  2. `storyboard-views`: the `## view <name>` sections are exactly the S2 names, each once, matched case-sensitively (Phase 1 FR-038); every beat row's `timeline` is an S2 name (§5.2 "one view section per view in S2, and no other").
  3. `storyboard-header`: the header lines of the storyboard template (`cli/mcp/knowledge/curriculum/storyboard.md`, "The template") agree with the brief (§5.2 "the providers with S6, the languages with L1, the assets with branch A, the host module with H1"):
     - `- provider:` lists, comma-separated before any `(`, exactly the distinct S6 providers (reading R-6: the template has one provider line, S6 one provider per view);
     - `- languages:` lists exactly the L1 codes, with `(default)` after the L1 default; `none` is accepted when L1 has one code;
     - `- assets:` lists exactly the keys of the asset list (Phase 1 FR-012) that are files or URLs (not the `<view>: <element>` and `font: <font>` placeholder keys); `none` exactly when there are none;
     - `- host module:` is `none` exactly when H1 is `none`.
  4. `storyboard-end-block`: every beat row has an `end-block` cell that is not empty and not `-` (§5.2 "every beat has an end block").
  5. `storyboard-interactions` (§5.2 "every navigation in S4, every key in I2, every control in I1 and every reaction in V6 has a row in the interactions table"):
     - each S4 row (`view`, `target`, `trigger`) has a row with verb `navigate`, target the S4 `target` and timeline the S4 `view`;
     - each I2 `key` has a row whose trigger is `key <key>` (case-insensitive);
     - I1 and V6 are free text (Phase 1 FR-006, `tree.ts:464`, `:476`), so they are checked by presence (R-7; no tree change, `TREE_VERSION` stays 1): when I1 is not `none`, at least one row has a verb among `play`, `pause`, `toggle`, `stop`, `seek`; for each view whose V6 is not `none`, at least one row with that view as `timeline` has a trigger that is not a `key`.
- **FR-030** **The storyboard reader** (`cli/mcp/storyboard.ts:66`) gains, without changing its existing fields, so `eligian_project` (its call in `storyboardOf`, `project.ts:481`) is unaffected: `header` (the `- provider:`, `- languages:`, `- assets:`, `- host module:` and `- audience:` values, trimmed, `undefined` when absent) and `views` (the names of the `## view <name>` headings, the text before ` (container` when present, in order). It still never throws.
- **FR-031** **After approval** the record gains the brief's program (R3, resolved from the project root) with `timelines` = the S2 names, `languages` = the L1 codes, `extensions` = H1 is not `none`, `via: brief` (§4.2 "a program enters the record only when its brief is approved"). It stays in the record if `BRIEF.md` is deleted later. Later edits to `STORYBOARD.md` do not close the gate (§5.2), unless the program or the storyboard gains a view: that is an addition (FR-034).

#### Additions (§4.3)

- **FR-032** **The three triggers**, measured per program by its text scan (FR-002) against the **approved set** (decision 7, §4.3):
  1. a timeline whose name is not in the approved set's timelines;
  2. a language code not in its languages;
  3. an `extensions` block where the approved set has none.

  The approved set of a governed, approved program is S2's names, L1's codes and H1 ≠ `none`, plus its approved additions (§4.3 "in a briefed project, not in the approved storyboard": at approval the storyboard's views are exactly S2, FR-029 item 2). Of a known, ungoverned program, and of every known governed program (FR-012 rows 3 and 4, whatever its brief's state), it is its record entry plus the approved additions of its directory's `BRIEF.md`. A new interaction, asset, beat, copy or style inside an existing view is not a trigger (§4.3 "A new interaction or a new asset inside an existing view is an edit, not an addition").
- **FR-033** **A storyboard view is a trigger too** in a briefed, approved directory: a `## view <name>` section of `STORYBOARD.md` whose name is not in the approved set (§5.2 "Later edits to the storyboard do not close the gate again, unless they add a view").
- **FR-034** **The refusal.** A program with a trigger is refused `addition-not-briefed` (§4.3). The payload's `additions` lists every trigger in program order (timelines, then languages, then the `extensions` block); `scope` and `round` are those of the first one that is not approved.
- **FR-035** **Addition sections in `BRIEF.md`.** Each addition is one section, `## Addition: view <name>`, `## Addition: language <code>` or `## Addition: host-module`, written after the branch and view sections and before `## Facts` (Phase 1 FR-019). It holds its own header list (`- state:`, the signed `- confirmation:` and `- approval:` lines of FR-024, their message lines) and its answers as `### <id>: <title>` blocks in Phase 1's answer format. In a project with no brief, `BRIEF.md` is created with the Phase 1 header lines (`# Brief`, the comment line, `- tree:`, `- state:`, `- confirmation: none`, `- approval: none`), no idea and no branch sections, then the addition sections (§4.3 "in a project that had no brief, the file is created with only that section"). Phase 1's parser keeps unknown `##` sections verbatim (Phase 1 FR-020); Phase 2 parses addition sections as such, and a file with no addition section round-trips byte-identically with Phase 1's writer (SC-018). In the engine `BriefState.additions` is optional (absent means none) and `EMPTY_BRIEF` has `additions: []`, so Phase 1's `BriefState` literals stay valid (build ruling, T013).
- **FR-036** **The scoped trees** (§4.3, the three lists). An addition's questions use the tree's ids and texts; the rows that §4.3 scopes to one view or one language are asked as that row:
  - **a view `<name>`**: V1–V6 for `<name>`; S4 as the rows whose `view` or `target` is `<name>` (a table, possibly `none`); S5, S6 and D5 as one record each (the table's columns without `view`); I4 when the presentation then has more than one view; A1–A6 for the assets the addition names (its V3 and S6 rows), with Phase 1's applies-when rules.
  - **a language `<code>`**: L2 as one record (`supplier`, `when`), L3, L4 and L5.
  - **a host module**: H1 (not `none`), H2, H3.

  Everything else is read from the existing code or brief as facts (§4.3). A rule that reads a question with no brief answer and no fact (for example V6's C3 in a project without a brief) evaluates as applying: the server asks rather than assumes (reading R-8). Answer validation, rejections, rounds and staleness are Phase 1's (FR-005 to FR-017, FR-039, FR-040), applied to the scoped questions; the S2 name rule of FR-047 applies to `<name>`, and `<name>` must not already be a view.
- **FR-037** **`scope`.** `eligian_brief` accepts `scope`: `'presentation'` (default), `{ addition: 'view' | 'language' | 'host-module', name: string }` (`name` is the view name or the language code; for `host-module` it is ignored) or `'adopt'` (§4.1). With an addition scope, `status`, `answer`, `confirm` and `approve-storyboard` act on that addition's section, which `status` or `answer` creates on first use. An addition scope is refused with `not-an-addition` when the name is already in the approved set. `status` with an addition scope is refused with `brief-not-approved` only for a **new presentation still in its interview**: the directory's main brief is not approved, it is not an adopted brief (FR-041), and no program of the directory is in the record (an open brief is changed by its own answers, not by additions). In every other directory the addition is measured against the record, as FR-032 does for known, ungoverned programs:
  - during an adoption that is not yet approved, the programs are existing work (FR-011, FR-048), so an addition to them takes the addition path they had before (§4.4 "Adopting never closes the gate on a program that was open"); the gate's `scope` for that case leads to a call that is accepted (SC-009);
  - after approval, and for a known program under FR-012 rows 3 and 4, the same holds, whatever the main brief's current computed state.
- **FR-038** **Confirming an addition** follows FR-018 to FR-027 over the addition's answers, with `section` = its heading in the HMAC.
- **FR-039** **Approving an addition's storyboard section** checks only what the addition touches (§4.3 "its storyboard section approved in the same way as a whole brief"): `STORYBOARD.md` exists and has no ignored rows; for a view, a `## view <name>` section, every beat of `<name>` with an end block, and an interactions row for each of the addition's S4 rows; for a language, `<code>` in the `- languages:` line; for a host module, a `- host module:` line that is not `none`.
- **FR-040** **After an addition is approved**, every known program of the directory gets the added timeline name, language code or `extensions: true` in its record entry, `via: addition` (§4.2 "when an addition to it is approved"). The approved addition also counts for programs written later in that directory (FR-032).

#### Adoption (`brief/adopt.ts`, §4.4)

- **FR-041** **The call.** `eligian_brief` with `scope: 'adopt'` and `action: 'status'` adopts the presentation in `directory` (§4.4 "the agent calls `eligian_brief` with `scope: adopt`"). The directory must hold exactly one program file (non-library `.eligian`, not recursive); otherwise the reply is `refused: { code: 'adopt-program' }` naming what was found. A directory whose `BRIEF.md` already holds a main brief that is not adopted is refused `adopt-briefed`. The new `BRIEF.md` header gains `- scope: adopt`.
- **FR-042** **The facts** (§4.4 "the views (S2), the entry view (S3), the navigation (S4), the providers (S6), the languages (L1), the assets and whether they exist, the host module (H1), the keys (I2) and the transport controls (I1)"), read under the compiler lock from the loaded program (`withLoadedDocuments`, `packages/language/src/compiler/index.ts:91`), the compiled config (`compileFile`, `cli/compile-file.ts:247`) and `eligian_project`'s inventory functions. Imports: `withLoadedDocuments` and `hostModuleOf` come from the `@eligian/language` root, as `project.ts:22` and `:29` import them (the `@eligian/language/mcp` entry does not export them); `timelineNames`, `timelineNamed` and `navigatesTo` come from `@eligian/language/mcp` (as `compile-file.ts:25` imports `timelineNames`). They are recorded as answers with `- by: code` (a third `by` value beside `user` and `delegated`, Phase 1 FR-019), in the tree's canonical shapes:
  - **S2**: one row per timeline (`timelineNames`, `packages/language/src/compiler/timeline-review.ts:178`), `purpose` `-`
  - **S3**: the first timeline (the entry, `storyboard.md` "From rows to code"), when there is more than one
  - **S4**: one row per `navigate` interaction (`InteractionStatement`, `packages/language/src/generated/ast.ts:846`): `view` = its timeline, `target`, `trigger` = `click <selector>` / `<event> <selector>` / `key <keys>`; an interaction inside an action counts for each timeline that calls that action, directly or through other actions (reading R-9)
  - **S6**: one row per timeline: `provider`, `source` (`timelineNamed(...).source`, `packages/language/src/lsp/timeline-symbols.ts:70`) or `-`
  - **L1**: the `languages` block's codes, `default` on the `*` entry; no fact when there is no `languages` block (L1 is then asked)
  - **I1**: the `play`, `pause`, `toggle`, `stop` and `seek` interactions, as text, or `none`
  - **I2**: one row per `key` interaction (`key`, `action` = `<verb> <target or position or call>`), or no fact when there is none
  - **H1**: one row `other` with the declared host names (`hostModuleOf`, defined at `packages/language/src/compiler/operations/host-operations.ts:115`, imported from the `@eligian/language` root) when there is an `extensions` block, else `none`
  - **R3**: the program's path from the project root
  - **V2**, **V3**, **V5**, **V6** per view (reading R-10; §4.4 names V1 and V4 as the per-view frontier, so these are what the code settles): V2 `in the code: <program file>`; V3 the view's media source (`video`/`audio`) and, on the entry view, the named asset imports (kind `image` for `.png .jpg .jpeg .gif .svg .webp`, else `other`), or `none`; V5 `duration` = the compiled timeline duration in seconds (`none` with pacing `none` when it is 0 or the program does not compile), `pacing` `fixed`, `cues-from` `-`; V6 the non-`key` interactions of that view as text, or `none`.

  The asset list and its states follow from these values as in Phase 1 FR-012.
- **FR-043** **The frontier** is then every question that applies and that no fact settles: purpose, context of use, the design intent, accessibility, delivery, the working agreement, V1 and V4 per view, and the remaining structure, interaction, language and asset questions (§4.4 "the frontier is then every question that applies and that the code does not settle"). No question settled by a fact is ever in a round (§8 exit "whose frontier holds only undecided questions").
- **FR-044** **When facts are read.** Facts are read at the adopting `status` call and again at every later call that passes `scope: 'adopt'`; a re-read replaces every `by: code` answer and gives each changed one the call's round (Phase 1 FR-015, so its dependents reopen). Calls without `scope: 'adopt'` read the facts from the file. Only these calls load the program: they take the compiler lock (`CompilerLock`, `cli/mcp/compiler-lock.ts:59`) for the read, and `eligian_brief` is wired through the server's `call` (which provides the lock, `server.ts:131–142`) instead of `boundary`. Every other `eligian_brief` call still touches neither the Langium services nor the lock (Phase 1 FR-032).
- **FR-045** **Facts cannot be answered.** An `answer` for an id that a fact settles is rejected with a new reason `fact` ("settled by the code; change the code and call with scope adopt again"). The engine counts fact-settled instances as answered, and the reply's counts gain `fromCode`. In the engine `Counts.fromCode` is optional, present only when above 0, so Phase 1's exact count expectations hold; the tool's reply always carries it (`counts.fromCode ?? 0`). The `eligian_brief` reply schema accepts `fact` from the moment the engine can produce it (build ruling, T013).
- **FR-046** **Conflicts** (§4.4 "Where a fact and an answer disagree …, the server reports the conflict in the reply; the user decides which one changes"). The reply's `conflicts` lists `{ ids, message }` for each rule that holds (reading R-11):
  - C3 has no `keyboard` and I2 has a fact row;
  - C3 has neither `mouse` nor `touch` and S4 or a V6 fact has a non-`key` trigger;
  - C5 is `offline` and an S6 `source` or a V3 `file` is an `http:`/`https:` URL.

  Conflicts do not block `confirm`; they are listed in the confirmation dialog (FR-019) and the reply until one side changes.
- **FR-047** **View names from code.** Timeline names in real programs contain characters that Phase 1's S2 rule rejects (`tree.ts:172`, `/^[A-Za-z0-9][A-Za-z0-9 _-]{0,63}$/`; the tour has `Timeline & Time` and `Files & Imports`, `examples/eligian-tour/tour.eligian:209`, `:630`). The rule is widened, for answers and facts alike, to any name of 1 to 64 characters with no `:`, `|`, line break, or leading or trailing space (`:` and `|` stay out for the `V<n>:<name>` ids and the tables, Phase 1 FR-010). `TREE_VERSION` stays 1: no question is added (Phase 1 FR-018). A program with a timeline name outside the widened rule is refused `adopt-program` naming it.
- **FR-048** **Adoption never closes the gate** (§4.4). Until the adopted brief is approved, its programs are existing work under FR-012, and they keep their record entries.
- **FR-049** **Approving an adopted brief.** It is confirmed as in FR-020 to FR-027. When `<directory>/STORYBOARD.md` exists when the brief is confirmed, it is not approved again: the confirming call also writes the approval line with mode `existing-storyboard` (§4.4 "When a `STORYBOARD.md` exists, it is not approved again"). Otherwise the agent drafts one and `approve-storyboard` applies with all of FR-029. On approval, the record entry is refreshed from the program's scan with `via: adopted`, and the directory is briefed: additions are measured against the approved set (§4.4 "After adoption the project is a briefed project").

#### The CLI warning (§4.5)

- **FR-053** **When.** `eligian check`, `compile`, `smoke`, `fmt` and `dev` print one line on stderr for each program they run on (libraries excluded) that is governed by a `BRIEF.md` whose state is not `approved` (FR-011, FR-026) and is not existing work (below), or that is not in the record when a record exists (§4.5). The record is the nearest `.eligian/programs.json` found walking up from the program's directory; with none, no not-known line is printed. Additions are not reported (§4.5 names only the two cases). `dev` prints its line once, at start.
  - **The same rule as the gate for existing work** (FR-012 rows 3 and 4): a governed program prints no line when it is in the record, whatever its `via` and whatever its brief's state (a known program is existing work). Where no record exists, the CLI cannot tell existing work from new work: it treats an ungoverned program as known (it prints no line, and no not-known line, §4.5) and a governed program as not known, so rows 5 to 9 decide whether a line is printed; a clone of an approved, built presentation whose brief does not verify and which has no `.eligian/` therefore prints one line there (state `complete`), and prints none once the server has recorded the program. The warning is computed by the same pure `gateVerdict` (FR-012), ignoring the addition triggers: a line is printed exactly when the verdict is a refusal other than `addition-not-briefed`.
- **FR-054** **The line**, one format for both cases (§4.5 "the state, and the tool call that shows the open questions … A program that is not in the record of known programs (§4.2) gets the same line"): `eligian: <program> — BRIEF.md is <state>; the open questions: eligian_brief {"action":"status","directory":"<dir>"}`. `<state>` is the brief's computed state (`open`, `complete` or `confirmed`), or `none` for a program not in the record that no `BRIEF.md` governs; `<dir>` is the program's directory. Paths are relative to the working directory, with forward slashes. The `accept-existing` hint for work that did not come from the agent is in the gate's reply (FR-012 row 2, FR-017), not in the terminal line.
- **FR-055** **Nothing else changes.** Stdout, the exit code and every other stderr line are as without the warning (§4.5; decision 8). The line goes to `process.stderr` directly, so `--format json`, `github` and `ndjson` stay machine-readable, also where `smoke --format ndjson` redirects the console (`main.ts:455–458`). The warning path of `check`, `compile`, `smoke`, `fmt` and `dev` reads `BRIEF.md`, the record and the key; it never writes any of them and never creates the state directory or the key (FR-008, FR-023). The one CLI write is `eligian init`'s (FR-060). A failure to read or parse any of them prints nothing extra and changes nothing: for the CLI an unparsable record counts as no record (the gate instead reads it as a record with no programs, FR-006, because the gate must fail closed and the warning must not cry wolf), and an unreadable or unparsable `BRIEF.md` counts as no brief.

## Edge cases

- **Windows and Linux paths.** Record entries are root-relative with `/`; lookups use the comparison of `isInside` (`paths.ts:77–81`). The CLI's nearest-record walk stops at the filesystem root. The state directory default differs per platform (FR-023).
- **Concurrency on the shared Langium services.** The gate is a text scan plus a `BRIEF.md` parse and never loads a document or takes the `CompilerLock` (FR-014). Only adoption loads the program, under the lock (FR-044). Brief writes keep Phase 1's per-brief permit; record writes have their own per-root semaphore and the cross-process re-read (FR-007). An elicitation holds neither (FR-022).
- **Stdout purity.** The gate failure is a declared failure (a JSON-RPC result). The CLI warning goes to stderr only (FR-055). Elicitation is a server request frame on stdout, which is protocol (SC-014).
- **Missing files.** No record: first-run scan (FR-003); a record that vanished after this process saw it: no rescan (FR-005); no `BRIEF.md`: ungoverned (FR-011); no `STORYBOARD.md`: `storyboard-missing` (FR-028); no key: nothing verifies, and the server creates one on the first signing (FR-023), the CLI never does.
- **Stale caches.** None: the record, `BRIEF.md`, `STORYBOARD.md` and the key are read on every call (FR-005). The per-process "record seen" flag of FR-005 is the one piece of memory, and it can only make the gate stricter.
- **Restarts.** Every turn of a headless run starts a new server (`spikes.md` §4.1). The record and the signed lines are on disk, so a program the agent wrote in turn 3 is not existing work in turn 4 (`spikes.md` §5 item 1; SC-002).
- **Cold start time.** The first-run scan runs in the background; `initialize` does not wait for it, gated calls do (FR-003, SC-015). The key is created lazily at the first signing or the first `ticket` (FR-020), never at start (SC-006).
- **A client with no answer.** A dialog that never shows (the reported Cursor fault on Windows, `spikes.md` §1.3) ends at the time limit (FR-021), with the permit free all along (FR-022).
- **An `Elicitation` hook answers for the user.** The server cannot tell it from a person (§9 risk 11); the mode recorded is `elicitation`. Phase 3's hook guards the settings file (§6.3).
- **An agent that runs code.** An agent with a shell can read the key in the user's state directory and compute an HMAC. §5.3 rules out typing an approval in with an editor; it does not stop an agent that executes code. The recorded mode, both dialogs and the Phase 3 hook are the remaining guards (§9 risk 4).
- **Two programs in one directory.** Both are governed by its `BRIEF.md` (FR-011); adoption needs exactly one (FR-041).
- **Hand edits.** Before approval, a hand-edited answer breaks the signature and gives `brief-not-confirmed`, not `brief-changed`, because its round did not move (FR-026), unless the program is already known (FR-012 rows 3 and 4: a known program is existing work whatever its brief's state). After approval, hand edits to `BRIEF.md` never close the gate; only additions do (FR-012 row 3, R-4). A hand edit to the record is read as is (R-13).
- **A clone of an approved, built presentation.** `.eligian/` ignores itself, so the clone has no record; the first-run scan records the program (`via: first-run`), its brief does not verify with the new user's key, and FR-012 row 4 lets it run; once the record exists the CLI prints no warning for it, and before it exists (no server has run there) the CLI prints one line with state `complete` (FR-053). A new program written in that clone's directory is not known and is asked to re-confirm (§5.3).
- **`eligian init` then a server.** The CLI's record (FR-060) lists no `main.eligian`, so the starter is unknown; the server finds the record and does not scan (FR-003). A server started in a project with no record, whose `cwd` is a filesystem root or the home directory, scans nothing and records nothing (FR-062).
- **A program edited while the user is asked.** For `accept-existing` the scans are compared after the dialog (FR-063); for `confirm` and `approve-storyboard` the files' bytes are (FR-022).
