## Overview

Phases 1 and 2 built the interview and made it binding: `eligian_brief` hands out rounds and records answers in `BRIEF.md`, both sign-offs go through elicitation with a fallback, and the five generation tools refuse until the brief is approved. Nothing yet teaches the agent to interview well, nothing stops an agent that writes a program with its own editor, and nothing measures whether the interview works with a real model. Phase 3 adds those three things:

- **Teaching** (§6.1, §6.2): a fourth server instructions string whose first workflow line puts `eligian_brief` first and that adds the rule "decisions are the user's, facts are the agent's"; the `new-presentation` prompt rewritten so steps 1 and 2 are the interview, the storyboard draft and its approval; a new `add-to-presentation` prompt; a new docs chunk `interview`; the `storyboard` chunk changed (its header derived from the brief, the approval step); the `AGENTS.md` block repeating the new instructions.
- **The hook** (§6.3): a new CLI subcommand `eligian brief gate` that reads a Claude Code `PreToolUse` hook's input and blocks four kinds of agent write (to `BRIEF.md`; a new program `.eligian` file whose brief is not approved; a hook that answers an elicitation added to any Claude settings file; `.eligian/programs.json`), and the Claude Code plugin (`plugins/claude/eligian/`) shipping it as `hooks/hooks.json` behind a dependency-free `hooks/prefilter.cjs` that starts the CLI only for those four kinds of target, with its server entry moved to `eligian@^1.2`.
- **The evals** (§7.1, §7.2): a `brief.md` fixture for each of the 14 existing cases, which the harness writes into the run's project as a confirmed brief and whose storyboard approval an `Elicitation` hook gives; a multi-turn interview harness in which a second model plays the user from a persona sheet; three personas.
- **Docs**: `packages/cli/README.md` and `CHANGELOG.md` describe the brief, the gate, the sign-offs, the CLI warning, `eligian brief gate` and the plugin hook.

Exit (roadmap §8 Phase 3, verbatim): "the success criterion of §1 on the three personas (3 runs each, majority); the 14 cases at their previous pass rate." Plus the one check the roadmap left **[UNVERIFIED]** for this phase (§6.3, §9 "Open questions"): "That the hook also runs when the plugin is installed from the marketplace, not loaded with `--plugin-dir`. Test: the Phase 3 exit, `/plugin install eligian@eligian` from this repo." All three are runs under the user's Claude subscription, never in CI (§7.2, spec 058 decision 9), so they are SC-001 to SC-003, recorded as `pending-user` in compliance.md the way Phase 2's SC-013 was; every piece of deterministic logic they rely on has an automated stand-in in CI (SC-004 onward, SC-020). Because these three ARE the roadmap's exit, a green build does not meet it: compliance.md and the roadmap §8 status line say so in words (SC-021), so Phase 3 never reads as having met its exit before the three runs pass.

## User scenarios and testing

### User story 1: the agent interviews well because it is taught to (P1)

**Acceptance scenarios**:
1. **Given** a fresh session with the server, **When** the agent reads the server instructions, **Then** the first workflow line tells it to call `eligian_brief` first for a new presentation and for an addition, and that nothing is written before the brief is approved.
2. **Given** the `new-presentation` prompt with an idea, **When** the agent follows it, **Then** its first steps are the interview (rounds with recommendations), the confirmation, the storyboard draft and its approval, and only then `eligian_init`.
3. **Given** an existing presentation, **When** the user runs the `add-to-presentation` prompt with "a closing view called Outro", **Then** the steps lead to `eligian_brief` with `scope: { addition: 'view', name: 'Outro' }`.
4. **Given** the `interview` chunk, **When** the agent forms a round, **Then** it knows the round format, where recommendations come from, which questions are facts it looks up, how to record "you decide", and how to present the sign-off.

### User story 2: an agent cannot write around the interview in Claude Code (P1)

**Acceptance scenarios**:
1. **Given** the plugin installed and no approved brief in `talk/`, **When** the agent tries to `Write` `talk/main.eligian`, **Then** the write is blocked and the agent receives the reason and the `eligian_brief` call to make.
2. **Given** any project, **When** the agent tries to `Write` or `Edit` a `BRIEF.md`, **Then** the write is blocked: only `eligian_brief` writes it.
3. **Given** any project, **When** the agent tries to add an `Elicitation` hook (or a hook on another event that can answer an elicitation) to a `.claude/settings.json` or `.claude/settings.local.json`, in the project or in the user's home, **Then** the write is blocked.
4. **Given** any project, **When** the agent tries to write `.eligian/programs.json`, **Then** the write is blocked.
5. **Given** an approved brief in `talk/`, **When** the agent writes `talk/main.eligian`, or edits an existing program, or writes a library file, **Then** nothing is blocked.

### User story 3: the evals measure the interview and still measure generation (P1)

**Acceptance scenarios**:
1. **Given** the case `title-card`, **When** the harness runs it in arm A1, **Then** the project starts with a confirmed `BRIEF.md` from the case's fixture, the agent drafts `STORYBOARD.md`, its `approve-storyboard` is accepted by the harness's `Elicitation` hook, and the run is gated and scored as before.
2. **Given** the persona `vague`, **When** the interview harness runs it, **Then** the simulated user answers from the sheet, changes an answer in a later round, accepts both sign-offs, and the run's record holds the six measures of §7.2.

Every tool name and docs id stays interpolated from `TOOL` / `DOC` (`prompts.ts:15–31`), and `NEW_PRESENTATION.tools` / `.docIds` (`:58–59`) gain `eligian_brief` and `interview` (spec 058 SC-012: "the arrays and the text have one source"). #### `eligian brief gate` (`main.ts`, `brief/hook-gate.ts`, §6.3)

- **FR-013** **The subcommand.** `eligian brief gate` is a new commander command group `brief` with one subcommand `gate`, registered as `agents` → `setup` is (`main.ts:533–546`). It takes no arguments. It reads one JSON object from stdin (the Claude Code `PreToolUse` hook input: `tool_name`, `tool_input`, `cwd`; `spikes.md` §3.1 "The hook input carries `tool_name` and `tool_input.file_path` as an absolute path") and exits:
  - `0` with nothing on stdout or stderr when the write is allowed;
  - `2` with the reason on stderr (one paragraph, ending "This hook comes from the eligian Claude Code plugin.") when it is blocked. Exit code 2 is the documented blocking code: the write is not made and the agent receives the stderr text (measured, `spikes.md` §3.1 "the write was blocked and the file was not created. The agent received the hook's message").
  It never writes to stdout, never writes a file, never creates the key or the state directory, and never loads documents into the Langium services (§6.3 "The hook reads only what is on disk (`BRIEF.md` and its signature), so it works without the running server").
- **FR-014** **What it inspects.** Only `tool_name` values `Write`, `Edit` and `MultiEdit` (Claude Code's file-writing tools for text files; reading R-1). Any other tool name, a missing or non-string `tool_input.file_path`, or stdin that is not a JSON object: exit 0 (the hook guards four targets only and must not block the session's other work; reading R-2). A relative `file_path` resolves against the input's `cwd`, else against the process's working directory.
- **FR-015** **Matching paths.** File names are compared case-insensitively on Windows and case-sensitively elsewhere, as Phase 2 matches `BRIEF.md` (Phase 2 FR-011, SC-020); both `\` and `/` separators are accepted.
- **FR-016** **Rule 1: `BRIEF.md`** (§6.3 "the target is `BRIEF.md` (only `eligian_brief` writes it)"; §4.6 "The agent does not write `BRIEF.md` with its own editor"). Any `Write`, `Edit` or `MultiEdit` whose target's base name is `BRIEF.md` is blocked, whether or not the file exists. The reason names `eligian_brief` with `action: answer` as the way to change an answer.
- **FR-017** **Rule 2: a new program before approval** (§6.3 "the target is a new `.eligian` file in a directory whose brief is not approved"). A `Write` whose target ends in `.eligian` and does not exist yet is evaluated as the program it would create:
  - its text is `tool_input.content`, scanned with `scanProgram` (`cli/mcp/brief/known-programs.ts:124`); a library (`scan.library`) is allowed (§4.2 "`library` files are not presentations and are not gated");
  - otherwise the verdict is Phase 2's pure `gateVerdict` (`cli/mcp/brief/gate.ts:181`) with that scan, no record entry (a file that does not exist is never known, §4.2), and the governance of the target's directory as the gate reads it (`BRIEF.md` in that directory, Phase 2 FR-011; the key from `stateDirectory()`, `signature.ts:69`, read with `readKey`, `signature.ts:113`; the project root from `findRecordFile`, `known-programs.ts:262`, else the target's directory);
  - it is blocked when the verdict is a refusal other than `addition-not-briefed`, the same rule as the CLI warning (Phase 2 FR-053: "a line is printed exactly when the verdict is a refusal other than `addition-not-briefed`"). The reason names the code, the brief's state and the `eligian_brief` call to make (the gate's `next` text for that code). An addition inside an approved directory is left to the gate (`addition-not-briefed` on the next `eligian_check`), because the hook's rule is "a directory whose brief is not approved".
  - An `Edit` or `MultiEdit` of an existing `.eligian` file, and a `Write` that replaces an existing one, are not rule 2's targets (edits are free, decision 7; the gate handles additions).
  - A read failure of `BRIEF.md` other than a missing file blocks (the rule fails closed for its own target; reading R-2).
  - **No record and no `BRIEF.md`**: a new program file in a project with no `.eligian/programs.json` (found by `findRecordFile`) and no governing `BRIEF.md` is blocked with `brief-required`, as the server gate's table row 2 refuses an unknown file (§4.2; §9 risk 3: a program written before the server's first call). `newProgramVerdict` does not copy the CLI warning's no-record shortcut (`gate.ts:731–733`, which treats such a program as known and prints nothing): in a project that has never run the server, a new program needs `eligian_brief` first.
- **FR-018** **Rule 3: a hook that answers an elicitation, in any Claude settings file** (§6.3 "it refuses a write to `.claude\settings.json` that adds an `Elicitation` hook. Such a hook answers an elicitation instead of the user (`spikes.md` §4.2), so it would approve every brief unseen"; §9 risk 11; decided in Clarifications, Q4, which widens §6.3's file and event). **The targets** are every file whose last two path segments are `.claude/settings.json` or `.claude/settings.local.json` (FR-015's matching, either separator), wherever it lies: the project's, and the user's own (`<home>/.claude/settings.json`, `<home>/.claude/settings.local.json`) included. **The guarded events** are `Elicitation` and every other hook event that Claude Code's documentation lists as able to answer or rewrite an elicitation (for example `ElicitationResult`); the list is fixed in plan.md with a citation of that documentation, and held in `hook-gate.ts` as `ELICITATION_HOOK_EVENTS: readonly string[]`. The hook computes the file's text after the write: `tool_input.content` for `Write`; the current text with `old_string` replaced by `new_string` (every occurrence when `replace_all` is true, else the first) for `Edit`; each of `edits` applied in order for `MultiEdit`. The write is blocked when, for any event `E` in `ELICITATION_HOOK_EVENTS`, the resulting JSON's `hooks.E` holds a hook command that the current file's `hooks.E` does not (an absent file has none). When the result is not valid JSON and its text contains any of those event names in double quotes, it is blocked (it cannot be judged). Every other change to a settings file is allowed.

- **FR-038** **The persona facts and what measure 2 checks.** A persona's facts are its `states` entries. ## Edge cases

- **Windows and Linux paths.** The hook's targets come as absolute paths (`spikes.md` §3.1); on Windows they carry backslashes and any drive-letter case. Name matching is case-insensitive on Windows only (FR-015), as Phase 2 matches `BRIEF.md` (Phase 2 SC-020). The settings and record targets are matched by their last two path segments with either separator; a settings file in the user's home `.claude` is a target like any other (FR-018). CI runs on Linux only, so these rules are tested through `hookDecision`'s `platform` argument (SC-007). The interview harness and the case harness run on Windows (the user's machine) and use `claude.exe` without a shell, as `run.ts:318` notes; the hook scripts are run as `node <absolute path>`.
- **Concurrency on the shared Langium services.** `eligian brief gate` is a separate short-lived process that loads no document (FR-013, FR-020); it never touches a running server's services or its `CompilerLock`. Parallel `Write` calls run parallel hook processes; each only reads. The fixture signing (`confirmBriefFixture`) runs in the harness process before the agent starts, never concurrently with the server.
- **Stdout purity.** `eligian brief gate` and `prefilter.cjs` write nothing on stdout in either outcome (Claude Code reads a hook's stdout as JSON on exit 0); the reason goes to stderr. The `eligian mcp` server gains a prompt and a docs chunk and nothing that writes; `mcp-stdout.spec.ts` stays green (SC-016). The harness's `elicitation-hook.cjs` writes exactly one JSON object on stdout, as Claude Code requires of an `Elicitation` hook (`spikes.md` §4.2).
- **Missing files.** No `BRIEF.md` next to a new program: rule 2 blocks (`brief-required`). No key in the state directory: nothing verifies, so a new program under a brief signed elsewhere is blocked, as the gate refuses it (§5.3 "A brief confirmed on another machine, with no program written yet, is asked to be confirmed again"). An absent settings file before a `Write`: its current `Elicitation` hooks are none. An absent `.eligian/programs.json`: rule 2 uses the target's directory as the root. A missing persona sheet, brief fixture or hook script is a named setup failure of the run, not a crash (the pattern of `materialiseFixtures`, `gate-steps.ts:59`).
- **Stale caches.** None: the hook reads `BRIEF.md`, the key and the record from disk on every invocation; the interview harness reads `BRIEF.md` after every turn; the server keeps no state across turns (FR-036).
- **Cold start time.** A write that is none of the four guarded kinds costs only the start of `node` for `prefilter.cjs` (FR-047, SC-008: median under 1 s), whatever the project. A guarded write pays `npx` resolution plus the CLI bundle's load (bounded by SC-008, 3 s, as `initialize`); `npx` against a local install avoids a download (R-4). The bundle loads `@eligian/language` at import (`main.ts:11`), so the budget is the bundle's, not the rule's.
- **A hook that cannot run.** When `npx` cannot resolve `eligian@^1.2` (offline with no cache, before publishing), `npx` exits non-zero and the prefilter passes that code on (or exits 1 when `npx` cannot be started, FR-047), Claude Code reports a non-blocking hook error and the write proceeds; the server's gate still refuses the generation tools (§2: tool results are the main lever, the hook is the hard stop on top).
- **An agent that runs code.** Writes through `Bash` bypass the hook (§9 risk 2), and an agent with a shell can read the key (Phase 2 edge case). The hook narrows the editor path; the recorded confirmation mode and the dialogs remain the guards (§9 risk 4).
- **An `Elicitation` hook in the eval project.** The harness writes it itself, not the agent, so the plugin's rule 3 does not apply (the eval runs load no plugin and no user settings, FR-048). The server cannot tell the hook's answer from a person's (§9 risk 11); the records name the hook's answers (`elicitations.log`).
- **Headless restarts.** The server starts on every turn of the interview eval (`spikes.md` §4.1); the record and the signed lines are on disk (FR-036), and the first turn's first-run scan records an empty project, so a program the agent writes in a later turn is never existing work (Phase 2 SC-002).
- **The simulated user goes off script.** It may answer a question that is not on the sheet, or volunteer facts; the sheet's rule "anything else: you decide" (FR-039) bounds it. Measure 2 checks the sheet's entries and every answer off the sheet (which must be `by: delegated` or `by: code`, FR-038), so an answer the agent recorded `by: user` for a question the persona never answered fails.
