## Overview

Phases 1 and 2 built the interview and made it binding: `eligian_brief` hands out rounds and records answers in `BRIEF.md`, both sign-offs go through elicitation with a fallback, and the five generation tools refuse until the brief is approved. Nothing yet teaches the agent to interview well, nothing stops an agent that writes a program with its own editor, and nothing measures whether the interview works with a real model. Phase 3 adds those three things:

- **Teaching** (§6.1, §6.2): a fourth server instructions string whose first workflow line puts `eligian_brief` first and that adds the rule "decisions are the user's, facts are the agent's"; the `new-presentation` prompt rewritten so steps 1 and 2 are the interview, the storyboard draft and its approval; a new `add-to-presentation` prompt; a new docs chunk `interview`; the `storyboard` chunk changed (its header derived from the brief, the approval step); the `AGENTS.md` block repeating the new instructions.
- **The hook** (§6.3): a new CLI subcommand `eligian brief gate` that reads a Claude Code `PreToolUse` hook's input and blocks four kinds of agent write (to `BRIEF.md`; a new program `.eligian` file whose brief is not approved; an `Elicitation` hook added to the project's Claude settings; `.eligian/programs.json`), and the Claude Code plugin (`plugins/claude/eligian/`) shipping it as `hooks/hooks.json`, with its server entry moved to `eligian@^1.2`.
- **The evals** (§7.1, §7.2): a `brief.md` fixture for each of the 14 existing cases, which the harness writes into the run's project as a confirmed brief and whose storyboard approval an `Elicitation` hook gives; a multi-turn interview harness in which a second model plays the user from a persona sheet; three personas.
- **Docs**: `packages/cli/README.md` and `CHANGELOG.md` describe the brief, the gate, the sign-offs, the CLI warning, `eligian brief gate` and the plugin hook.

Exit (roadmap §8 Phase 3, verbatim): "the success criterion of §1 on the three personas (3 runs each, majority); the 14 cases at their previous pass rate." Plus the one check the roadmap left **[UNVERIFIED]** for this phase (§6.3, §9 "Open questions"): "That the hook also runs when the plugin is installed from the marketplace, not loaded with `--plugin-dir`. Test: the Phase 3 exit, `/plugin install eligian@eligian` from this repo." All three are runs under the user's Claude subscription, never in CI (§7.2, spec 058 decision 9), so they are SC-001 to SC-003, recorded as `pending-user` in compliance.md the way Phase 2's SC-013 was; every piece of deterministic logic they rely on has an automated stand-in in CI (SC-004 onward, SC-020). Because these three ARE the roadmap's exit, a green build does not meet it: compliance.md and the roadmap §8 status line say so in words (SC-021), so Phase 3 never reads as having met its exit before the three runs pass.

## User scenarios and testing

### User story 1: the agent interviews well because it is taught to (P1)

**Acceptance scenarios**:
1. **Given** a fresh session with the server, **When** the agent reads the server instructions, **Then** the first workflow line tells it to call `eligian_brief` first for a new presentation and for an addition, and that nothing is written before the brief is approved.
2. **Given** the `new-presentation` prompt with an idea, **When** the agent follows it, **Then** its first steps are the interview (rounds with recommendations), the confirmation, the storyboard draft and its approval, and only then `eligian_init`.
3. **Given** an existing presentation, **When** the user runs the `add-to-presentation` prompt with "a closing view called Outro", **Then** the steps lead to `eligian_brief` with `scope: { addition: 'view', name: 'Outro' }`.
4. **Given** the `interview` chunk, **When** the agent forms a round, **Then** it knows the round format, where recommendations come from, which questions are facts it looks up, how to record "you decide", and how to present the sign-off.

### User story 2: an agent cannot write around the interview in Claude Code (P1)

**Acceptance scenarios**:
1. **Given** the plugin installed and no approved brief in `talk/`, **When** the agent tries to `Write` `talk/main.eligian`, **Then** the write is blocked and the agent receives the reason and the `eligian_brief` call to make.
2. **Given** any project, **When** the agent tries to `Write` or `Edit` a `BRIEF.md`, **Then** the write is blocked: only `eligian_brief` writes it.
3. **Given** any project, **When** the agent tries to add an `Elicitation` hook to `.claude/settings.json`, **Then** the write is blocked.
4. **Given** any project, **When** the agent tries to write `.eligian/programs.json`, **Then** the write is blocked.
5. **Given** an approved brief in `talk/`, **When** the agent writes `talk/main.eligian`, or edits an existing program, or writes a library file, **Then** nothing is blocked.

### User story 3: the evals measure the interview and still measure generation (P1)

**Acceptance scenarios**:
1. **Given** the case `title-card`, **When** the harness runs it in arm A1, **Then** the project starts with a confirmed `BRIEF.md` from the case's fixture, the agent drafts `STORYBOARD.md`, its `approve-storyboard` is accepted by the harness's `Elicitation` hook, and the run is gated and scored as before.
2. **Given** the persona `vague`, **When** the interview harness runs it, **Then** the simulated user answers from the sheet, changes an answer in a later round, accepts both sign-offs, and the run's record holds the six measures of §7.2.

## Requirements

### Functional requirements

#### Server instructions (`instructions.ts`, §6.1)

- **FR-001** **A fourth instructions string.** `INSTRUCTIONS` (`cli/mcp/instructions.ts:82`, today `Readonly<Record<1 | 2 | 3, string>>`) gains key `4`, and `MCP_PHASE` (`:14`, today `3`) becomes `4`, so `server.ts:242` serves the new string (§6.1 "A fourth instructions string (`packages\cli\src\mcp\instructions.ts`), within the 4,096-character limit"). Strings 1 to 3 stay byte-identical (their specs keep passing).
- **FR-002** **Its first workflow line** is the `eligian_brief` line, before the `eligian_docs` line: `eligian_brief` comes first for a new presentation and for an addition (a new view, a new language or a first host module, §4.3; the line contains the word "addition"); nothing is written before the brief is approved (the line contains the word "approved"); the generation tools refuse until then (§6.1 "Its first workflow line: `eligian_brief` comes first for a new presentation and for an addition; nothing is written before the brief is approved").
- **FR-003** **One new rule**, after the five engine rules (`instructions.ts:55–64`), beginning with the exact words "Decisions are the user's, facts are yours" (the instructions address the agent): the agent looks up what `eligian_project` or the files answer and asks the user only decisions, each with its recommendation (§6.1 "One new rule: decisions are the user's, facts are the agent's"; §1 "The agent looks up facts itself and puts only decisions to the user").
- **FR-004** **The docs line no longer puts the storyboard first.** Today's `DOCS_LINE` (`instructions.ts:24–29`) says `eligian_docs` is "FIRST for a new presentation: ids `storyboard`, `decisions`, `project-layout`, then write STORYBOARD.md". In string 4 the storyboard ids are read after the brief is confirmed, and STORYBOARD.md is drafted from the brief and approved with `approve-storyboard` (§5.2; decision 4 "the brief settles decisions; the agent drafts the storyboard; the user approves it; only then does generation start"). Strings 1 to 3 keep their `DOCS_LINE`.
- **FR-005** **Constraints** carried over from spec 058 (`mcp-instructions.spec.ts:100–108`, `:151–156`): string 4 is at most 4,096 characters (§9 risk 9), every backticked lowercase token is a tool or a docs id that exists (`eligian_brief` and the new `interview` id included), and all nine tools are named.
- **FR-006** **The `AGENTS.md` block repeats the instructions** (§6.1 "The `AGENTS.md` block that `eligian init` and `eligian agents setup` write repeats the instructions, as today"). `BLOCK_PARTS` (`instructions.ts:89`) gains key `4` with string 4's workflow and rules, so `agentsMdBlock` (`:134`), which reads `BLOCK_PARTS[MCP_PHASE]`, and the generated `dist/docs/agents-block.md` (`generate-knowledge.ts:1259`) carry them. `eligian init` and `eligian agents setup` write the block from that file as today (`agents.ts:265`); no change to how they merge it.

#### Prompts (`prompts.ts`, §6.1)

- **FR-007** **`new-presentation`**: "steps 1 and 2 become the interview, the storyboard draft and its approval" (§6.1). The prompt's text (`prompts.ts:33–49`) starts with: (1) call `eligian_brief` with `action: status` and the idea verbatim; (2) ask each round in one message, each question with a recommendation worded so that "yes" accepts it, look facts up instead of asking, record the replies with `action: answer`, until the state is `complete`; (3) `confirm` (the dialog, or the user's reply verbatim as `confirmation`); (4) read `storyboard`, `decisions` and `project-layout`, draft `STORYBOARD.md` from the brief and call `approve-storyboard`. The steps that follow are today's steps 3 to 12, in order and unchanged in content. Every tool name and docs id stays interpolated from `TOOL` / `DOC` (`prompts.ts:15–31`), and `NEW_PRESENTATION.tools` / `.docIds` (`:58–59`) gain `eligian_brief` and `interview` (spec 058 SC-012: "the arrays and the text have one source"). The argument stays one required non-empty `idea` (`:69–73`), and the text without the idea stays at most 4,096 characters (`mcp-prompts.spec.ts:103`).
- **FR-008** **`add-to-presentation`** (new; §6.1 "A new prompt `add-to-presentation` (arguments: what to add) for additions"). One required non-empty argument, `addition`: what to add, in the user's words. One user message: the addition, then numbered steps: (1) call `eligian_project` on the program to see its views, languages and host module; (2) decide which of the three additions it is (a new view, a new language, a first host module, §4.3); a change inside an existing view is an edit and needs no interview (decision 7); (3) call `eligian_brief` with `scope: { addition, name }` and `action: status`, interview as in `new-presentation` steps 2 to 4 (for the scoped round), `confirm`, add the storyboard section and `approve-storyboard`; (4) write the code, then `eligian_check`, `eligian_fmt`, `eligian_smoke` as in `new-presentation`. Its tools and docs ids are interpolated as FR-007 requires; at most 4,096 characters without the argument. It is registered beside `newPresentationPrompt` (`server.ts:233`) with `McpServer.prompt` (`prompts.ts:64–75` is the pattern; `@stability unstable`, roadmap §9 risk 6).

#### Docs chunks (§6.2)

- **FR-009** **`interview`** (new, `cli/mcp/knowledge/curriculum/interview.md`, frontmatter `kind: workflow`, as `storyboard.md:1–11`). Its content is §6.2's list: "the round format, how to form a recommendation from `decisions`, `provider-choice`, `presentation-patterns` and `css-conventions`, facts against decisions, delegated answers, and how to present the sign-off". Concretely: one message per round holding every question of the round, each with its title, the agent's recommendation worded so that "yes" accepts it, and the doc it came from; the facts of §3.1 (the project's ids, classes, custom properties, locale keys, assets and host declarations from `eligian_project`; whether a file exists; text direction from the language code; the installed `eligian` version and package manager) are looked up, never asked; "you decide" is recorded with `delegated: true` and the agent's choice as `value`, and every delegated answer is listed at sign-off; the sign-off summary shows the counts, the delegated answers and the `BRIEF.md` path, and a declined dialog means asking what to change; the fallback without elicitation passes the user's reply verbatim as `confirmation` (with the `ticket` when one was returned). It names `brief-questions` for the full tree. Its `see` ids exist (the generator checks them).
- **FR-010** **`storyboard`** (changed; §6.2 "`storyboard` (changed): the header is derived from the brief; the approval step"). The chunk's title, card and first heading stop saying "before any Eligian" first (`storyboard.md:3`, `:10`, `:13`); it says the storyboard is drafted after the brief is confirmed. A new section "Approval" says: call `eligian_brief` with `action: approve-storyboard`; the user approves in a dialog or by the fallback; later edits stay free unless they add a view (§5.2). Everything else in the chunk (the beat and interaction tables, "From rows to code", "Before declaring done", `storyboard.md:185–207`) stays.
- **FR-011** **`brief-questions`** (generated, Phase 1, `generate-knowledge.ts:804–831`) is unchanged; FR-009 and FR-010 link to it.

#### `eligian brief gate` (`main.ts`, `brief/hook-gate.ts`, §6.3)

- **FR-013** **The subcommand.** `eligian brief gate` is a new commander command group `brief` with one subcommand `gate`, registered as `agents` → `setup` is (`main.ts:533–546`). It takes no arguments. It reads one JSON object from stdin (the Claude Code `PreToolUse` hook input: `tool_name`, `tool_input`, `cwd`; `spikes.md` §3.1 "The hook input carries `tool_name` and `tool_input.file_path` as an absolute path") and exits:
  - `0` with nothing on stdout or stderr when the write is allowed;
  - `2` with the reason on stderr (one paragraph, ending "This hook comes from the eligian Claude Code plugin.") when it is blocked. Exit code 2 is the documented blocking code: the write is not made and the agent receives the stderr text (measured, `spikes.md` §3.1 "the write was blocked and the file was not created. The agent received the hook's message").
  It never writes to stdout, never writes a file, never creates the key or the state directory, and never loads documents into the Langium services (§6.3 "The hook reads only what is on disk (`BRIEF.md` and its signature), so it works without the running server").
- **FR-014** **What it inspects.** Only `tool_name` values `Write`, `Edit` and `MultiEdit` (Claude Code's file-writing tools for text files; reading R-1). Any other tool name, a missing or non-string `tool_input.file_path`, or stdin that is not a JSON object: exit 0 (the hook guards four targets only and must not block the session's other work; reading R-2). A relative `file_path` resolves against the input's `cwd`, else against the process's working directory.
- **FR-015** **Matching paths.** File names are compared case-insensitively on Windows and case-sensitively elsewhere, as Phase 2 matches `BRIEF.md` (Phase 2 FR-011, SC-020); both `\` and `/` separators are accepted.
- **FR-016** **Rule 1: `BRIEF.md`** (§6.3 "the target is `BRIEF.md` (only `eligian_brief` writes it)"; §4.6 "The agent does not write `BRIEF.md` with its own editor"). Any `Write`, `Edit` or `MultiEdit` whose target's base name is `BRIEF.md` is blocked, whether or not the file exists. The reason names `eligian_brief` with `action: answer` as the way to change an answer.
- **FR-017** **Rule 2: a new program before approval** (§6.3 "the target is a new `.eligian` file in a directory whose brief is not approved"). A `Write` whose target ends in `.eligian` and does not exist yet is evaluated as the program it would create:
  - its text is `tool_input.content`, scanned with `scanProgram` (`cli/mcp/brief/known-programs.ts:124`); a library (`scan.library`) is allowed (§4.2 "`library` files are not presentations and are not gated");
  - otherwise the verdict is Phase 2's pure `gateVerdict` (`cli/mcp/brief/gate.ts:181`) with that scan, no record entry (a file that does not exist is never known, §4.2), and the governance of the target's directory as the gate reads it (`BRIEF.md` in that directory, Phase 2 FR-011; the key from `stateDirectory()`, `signature.ts:69`, read with `readKey`, `signature.ts:113`; the project root from `findRecordFile`, `known-programs.ts:262`, else the target's directory);
  - it is blocked when the verdict is a refusal other than `addition-not-briefed`, the same rule as the CLI warning (Phase 2 FR-053: "a line is printed exactly when the verdict is a refusal other than `addition-not-briefed`"). The reason names the code, the brief's state and the `eligian_brief` call to make (the gate's `next` text for that code). An addition inside an approved directory is left to the gate (`addition-not-briefed` on the next `eligian_check`), because the hook's rule is "a directory whose brief is not approved".
  - An `Edit` or `MultiEdit` of an existing `.eligian` file, and a `Write` that replaces an existing one, are not rule 2's targets (edits are free, decision 7; the gate handles additions).
  - A read failure of `BRIEF.md` other than a missing file blocks (the rule fails closed for its own target; reading R-2).
- **FR-018** **Rule 3: an `Elicitation` hook in the project's Claude settings** (§6.3 "it refuses a write to `.claude\settings.json` that adds an `Elicitation` hook. Such a hook answers an elicitation instead of the user (`spikes.md` §4.2), so it would approve every brief unseen"; §9 risk 11). The targets are `.claude/settings.json` and `.claude/settings.local.json` (reading R-3). The hook computes the file's text after the write: `tool_input.content` for `Write`; the current text with `old_string` replaced by `new_string` (every occurrence when `replace_all` is true, else the first) for `Edit`; each of `edits` applied in order for `MultiEdit`. The write is blocked when the resulting JSON's `hooks.Elicitation` holds a hook command that the current file's `hooks.Elicitation` does not (an absent file has none). When the result is not valid JSON and its text contains `"Elicitation"`, it is blocked (it cannot be judged). Every other change to the settings files is allowed.
- **FR-019** **Rule 4: the record of known programs** (§6.3 "The hook has a fourth rule: it refuses an agent write to `.eligian/programs.json`. The record is not signed in Phase 2 (spec 059 phase 2, R-13), so without this rule an agent could add its own program to the record with its editor"). Any write whose target's base name is `programs.json` and whose parent directory's name is `.eligian` is blocked. The reason names `eligian_brief` with `action: accept-existing` as the way to add existing work.
- **FR-020** **Imports.** `brief/hook-gate.ts` imports `node:*`, `brief/gate.ts`, `brief/known-programs.ts`, `brief/signature.ts` and `brief/brief-file.ts` only; never `@eligian/language` and never `effect/ai` (Phase 2 FR-002 keeps `gate.ts` and `known-programs.ts` free of the language package; a grep test, SC-009). `main.ts` loads it with a dynamic `import()` inside the action, as `printBriefWarnings` loads `gate.js` (`main.ts:85`).
- **FR-021** **The governance read is shared, not copied.** Rule 2 needs the directory governance that `gate.ts` computes for the CLI warning (`governanceOf`, `gate.ts:430`, module-local today, and `nextOf`, `gate.ts:557`, module-local). `gate.ts` exports one function for it, for example `newProgramVerdict(file, source, env): Promise<{ verdict: Verdict; state; next; root } | undefined>` built from the same `governanceOf` and `gateVerdict` as `cliBriefWarnings` (`gate.ts:751`); no second copy of the matrix exists.

## Edge cases

- **Windows and Linux paths.** The hook's targets come as absolute paths (`spikes.md` §3.1); on Windows they carry backslashes and any drive-letter case. Name matching is case-insensitive on Windows only (FR-015), as Phase 2 matches `BRIEF.md` (Phase 2 SC-020). The settings and record targets are matched by their last two path segments with either separator. CI runs on Linux only, so these rules are tested through `hookDecision`'s `platform` argument (SC-007). The interview harness and the case harness run on Windows (the user's machine) and use `claude.exe` without a shell, as `run.ts:318` notes; the hook scripts are run as `node <absolute path>`.
- **Concurrency on the shared Langium services.** `eligian brief gate` is a separate short-lived process that loads no document (FR-013, FR-020); it never touches a running server's services or its `CompilerLock`. Parallel `Write` calls run parallel hook processes; each only reads. The fixture signing (`confirmBriefFixture`) runs in the harness process before the agent starts, never concurrently with the server.
- **Stdout purity.** `eligian brief gate` writes nothing on stdout in either outcome (Claude Code reads a hook's stdout as JSON on exit 0); the reason goes to stderr. The `eligian mcp` server gains a prompt and a docs chunk and nothing that writes; `mcp-stdout.spec.ts` stays green (SC-016). The harness's `elicitation-hook.cjs` writes exactly one JSON object on stdout, as Claude Code requires of an `Elicitation` hook (`spikes.md` §4.2).
- **Missing files.** No `BRIEF.md` next to a new program: rule 2 blocks (`brief-required`). No key in the state directory: nothing verifies, so a new program under a brief signed elsewhere is blocked, as the gate refuses it (§5.3 "A brief confirmed on another machine, with no program written yet, is asked to be confirmed again"). An absent settings file before a `Write`: its current `Elicitation` hooks are none. An absent `.eligian/programs.json`: rule 2 uses the target's directory as the root. A missing persona sheet, brief fixture or hook script is a named setup failure of the run, not a crash (the pattern of `materialiseFixtures`, `gate-steps.ts:59`).
- **Stale caches.** None: the hook reads `BRIEF.md`, the key and the record from disk on every invocation; the interview harness reads `BRIEF.md` after every turn; the server keeps no state across turns (FR-036).
- **Cold start time.** Every agent write in a Claude Code session with the plugin starts the hook: `npx` resolution plus the CLI bundle's load. The CLI's load is bounded by SC-008 (3 s, as `initialize`); `npx` against a local install avoids a download (R-4). The bundle loads `@eligian/language` at import (`main.ts:11`), so the budget is the bundle's, not the rule's.
- **A hook that cannot run.** When `npx` cannot resolve `eligian@^1.2` (offline with no cache, before publishing), Claude Code reports a non-blocking hook error and the write proceeds; the server's gate still refuses the generation tools (§2: tool results are the main lever, the hook is the hard stop on top).
- **An agent that runs code.** Writes through `Bash` bypass the hook (§9 risk 2), and an agent with a shell can read the key (Phase 2 edge case). The hook narrows the editor path; the recorded confirmation mode and the dialogs remain the guards (§9 risk 4).
- **An `Elicitation` hook in the eval project.** The harness writes it itself, not the agent, so the plugin's rule 3 does not apply (the eval runs load no plugin). The server cannot tell the hook's answer from a person's (§9 risk 11); the records name the hook's answers (`elicitations.log`).
- **Headless restarts.** The server starts on every turn of the interview eval (`spikes.md` §4.1); the record and the signed lines are on disk (FR-036), and the first turn's first-run scan records an empty project, so a program the agent writes in a later turn is never existing work (Phase 2 SC-002).
- **The simulated user goes off script.** It may answer a question that is not on the sheet, or volunteer facts; the sheet's rule "anything else: you decide" (FR-039) bounds it. Measure 2 checks the sheet's entries and every answer off the sheet (which must be `by: delegated` or `by: code`, FR-038), so an answer the agent recorded `by: user` for a question the persona never answered fails.
