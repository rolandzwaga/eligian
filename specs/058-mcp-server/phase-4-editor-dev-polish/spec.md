## Overview

Phases 0–3 shipped `eligian mcp` with eight tools, the curriculum, the review pass, smoke scenarios, determinism, the media clock, provenance and the eval harness. A client still has to be configured by hand or by `eligian init` / `eligian agents setup`, and `eligian dev` reports only build errors. Phase 4 closes the last user-facing gaps of the roadmap:

1. **VS Code registration with no user config** (§2 row (c), decision 2). The extension contributes `mcpServerDefinitionProviders` and registers an `McpServerDefinitionProvider`. In a trusted workspace whose folder has a workspace-local `eligian` ≥ 1.1, it provides an `McpStdioServerDefinition` that runs `node <folder>/node_modules/eligian/bin/cli.js mcp`. Copilot agent mode then lists the `eligian_*` tools with no `.vscode/mcp.json`.
   - Without such an install, the extension offers to install `eligian`.
   - Two settings: `eligian.mcp.enabled` turns the provider off, and `eligian.mcp.command` sets the program that starts the server.
   - In Cursor, the extension uses `vscode.cursor.mcp.registerServer` when that API is present.
   - No CLI copy goes into the `.vsix`.
2. **`dev` runtime feedback** (§4 "Deliberately NOT tools", first row). The dev page posts engine `error` events and console errors back to the dev server. The server prints them in the terminal, located through the Eligian map of the same build, and writes them to `.eligian/dev-errors.json` so an agent can read them.
3. **MCP resources and one prompt** (§3.4). Each docs chunk is served as an MCP resource `eligian://docs/<id>` for @-mention. There is one prompt, `new-presentation`.
4. **Polish**: the READMEs, the CHANGELOG, the `verification-ladder` chunk and the AGENTS.md lines that describe `dev` and the editor registration.

## User scenarios and testing

### User story 1: Copilot agent mode knows Eligian with no setup (P1)

A user opens a folder made by `eligian init` (with `eligian` ≥ 1.1 installed in it) in VS Code with the Eligian extension. They switch Copilot Chat to agent mode. The `eligian_*` tools are listed, and the user wrote no `.vscode/mcp.json`.

Acceptance:
1. Given a trusted folder with `node_modules/eligian/package.json` at version `1.1.0` and `node_modules/eligian/bin/cli.js`, when VS Code asks the provider, it gets exactly one `McpStdioServerDefinition`:
   - label `Eligian`;
   - command `node` (the default of `eligian.mcp.command`);
   - args `[<folder fsPath>/node_modules/eligian/bin/cli.js, 'mcp']`, with the platform's separators;
   - `cwd` = the folder `Uri`;
   - `version` = `1.1.0`.
2. Given the same folder after `npm install eligian@1.2.0`, the provider fires `onDidChangeMcpServerDefinitions`, and the next definition has `version` `1.2.0`.
3. Given `eligian.mcp.enabled: false`, the provider returns `[]`. Turning the setting on again fires the change event, and the definition comes back.

### User story 2: a folder without a usable install gets an offer, not a broken server (P1)

1. Given a trusted folder that contains `.eligian` files and no `node_modules/eligian`, or one at `1.0.x`, or a folder with no `.eligian` file yet but a `node_modules/eligian` at `1.0.x` (or without `bin/cli.js`), the provider returns no definition for it. The extension shows one notification: "Eligian tools for Copilot need `eligian` 1.1 or later in this folder", with the actions **Install** and **Don't Ask Again**.
2. **Install** opens a terminal in that folder and runs the install command of the package manager found by walking up from the folder (FR-035): `<pm> add -D eligian@^1.1`, or the plain `<pm> install` when the folder's `package.json` already declares an `eligian` range that admits 1.1 or later, as a fresh clone of an `eligian init` project does (FR-036). Once the install is done, the file watcher fires the change event, and the definition appears.
3. **Don't Ask Again** stores the choice in `workspaceState`. The notification does not appear again in that workspace.

### User story 3: an existing `.vscode/mcp.json` keeps working (P1)

1. Given a folder where `eligian agents setup --client vscode` wrote `.vscode/mcp.json` with `servers.eligian`, the agent sees the `eligian_*` tools once, from the file's server, and the provider adds no second Eligian server for that folder (FR-004, I-2).
2. Given `eligian.mcp.enabled: false` and the same file, the tools still come from the file.
3. Given a hand-written entry under another key (for example `"eligian-mcp"`) whose `args` run `.../eligian/bin/cli.js mcp` or `npx eligian mcp`, or an Eligian server in the workspace-level `mcp` configuration (`.code-workspace` or workspace settings), the provider adds no second Eligian server either (FR-004, FR-034).

### User story 4: `dev` tells the terminal (and the agent) where the page failed (P1)

1. Given `eligian dev main.eligian` and a program whose `on enter` calls a host operation that throws, when the page loads, the terminal prints a runtime error line with the message and `main.eligian:<line>:<column>` of the failing operation, and the timeline and the action names. `.eligian/dev-errors.json` holds the same entry.
2. Given a `console.error("x")` in the page (for example, from a host module), the terminal prints `console error: x` without a location. The file holds it with kind `console-error`.
3. Given a fix of the source, the rebuild (the one that sends `reload`) clears the errors of the old build from the file. The new page then reports afresh. A CSS-only change keeps the running page's build identity, so errors already in the file stay and the page's later reports are still located (FR-033).
4. Given a `console.warn("w")` in the page, the terminal prints `console warning: w` and the file holds it with kind `console-warn`. Given a `selectElement("#nope")` that matches no element, the terminal prints the selector miss located at the operation's source position (kind `selector-miss`), not as a `console-warn` (FR-039, FR-040).
5. Given the same error 50 times in one page load (a looping timeline), the terminal prints it once; the file holds one entry with `count: 50` (FR-038).

### User story 5: the docs are @-mentionable, and a prompt starts a presentation (P2)

1. In Claude Code, `@eligian:` lists `eligian://docs/map-dataflow` and the other chunks. Picking one inserts the chunk.
2. `/mcp__eligian__new-presentation "a 10-second title card"` inserts the workflow kickoff with the idea filled in.

## Requirements

### A. Extension registration (roadmap §7 Phase 4 Touches; §2 row (c); decision 2)

- **FR-001** The extension MUST contribute `contributes.mcpServerDefinitionProviders` with one entry, `{ "id": "eligian.mcp", "label": "Eligian" }`, and, unless the Cursor API is detected (FR-010/FR-011), MUST register the provider with `vscode.lm.registerMcpServerDefinitionProvider('eligian.mcp', provider)` during activation. On that (non-Cursor) branch the ids must be equal; a test reads `package.json` and asserts this. The registration MUST be in `registerClientIndependentFeatures` (`main.ts:78`), so that a language server that fails to start does not take it down. The disposable MUST be pushed to `context.subscriptions`. *(§7 Touches: "`vscode.lm.registerMcpServerDefinitionProvider` → `McpStdioServerDefinition`")*
- **FR-002** `provideMcpServerDefinitions` MUST return one `McpStdioServerDefinition` per workspace folder that satisfies all of:
  - (a) `eligian.mcp.enabled` is `true` for the folder;
  - (b) the workspace is trusted (FR-012);
  - (c) `<folder>/node_modules/eligian/package.json` exists, and its `version` has major.minor ≥ 1.1. The comparison is numeric on major and minor; a prerelease of 1.1.0 or later counts. A missing or unparsable `version` fails the check;
  - (d) `<folder>/node_modules/eligian/bin/cli.js` exists;
  - (e) the user has configured no Eligian server for the folder: the folder's `.vscode/mcp.json` has none (FR-004) and the workspace-level `mcp` configuration has none (FR-034).

### F. `dev` runtime feedback (§4 "Deliberately NOT tools", first row; §7 Touches `dev-server,client-runtime`)

- **FR-013** `createBundle` MUST return the `EligianMap` of the compile it bundled. - **FR-014** `dev-server.ts` MUST keep the map and config of the current reload-build (FR-033), and MUST accept `POST /__eligian/runtime` with a JSON body. The body is one of:

  Each report MUST carry the `buildId` the server sent with the page (FR-016). Status codes:
  - `204` for an accepted report, and also for a report whose `buildId` is not the current build's, which MUST be dropped (nothing printed, nothing written; a page from an old build is not an error);

  - (c) wrap `console.error` so that every call is posted as `console-error`, and still calls through; wrap `console.warn` the same way (posted as `console-warn`, or as `selector-miss` for Eligius' selector warning, FR-039), and still calls through;

  - (e) use `navigator.sendBeacon` where available, else `fetch(…, { method: 'POST', keepalive: true })`, and never throw or post recursively (an error inside the poster is swallowed);
  - (f) send at most 50 reports per page load, and after that one final `console-error` "eligian dev: more errors not forwarded".

  The `buildId` comes from the server: `index.html` gets it with the client tag (`withClient`), and every `reload` follows a new build (a CSS-only build sends no `reload` and keeps the `buildId`, FR-033). The existing behaviour (resume, `css`, `build-error` overlay) MUST NOT change (`dev-client.spec.ts` stays green).
- **FR-017** For an `engine-error`, the server MUST call `locateEngineError(map, { actionId, phase, operationSystemName, operationIndex, operationPath })`. ## Edge cases

- **Windows and Linux paths.** The definition's `args[0]` is `Uri.joinPath(folder, 'node_modules', 'eligian', 'bin', 'cli.js').fsPath`: backslashes and a drive letter on Windows, forward slashes on Linux. That is the same shape `detectServerCommand` produces with `path.resolve` (`agents.ts:58`). There is no shell (`McpStdioServerDefinition` "by default will not run in a shell environment"), so paths with spaces need no quoting. `.eligian/dev-errors.json` paths are absolute in the platform's form, and the terminal shows the location relative to the entry dir.
- **`node` not on the editor's PATH** (VS Code launched from a GUI on some systems): the server fails to start, and VS Code shows the start error. The fix is `eligian.mcp.command` (FR-007), and the README says so. The provider does not use `process.execPath`: in the extension host that is the editor's Electron binary, which needs `ELECTRON_RUN_AS_NODE` and carries the editor's Node version instead of the CLI's `>=22.12.0`.
- **Symlinked installs** (pnpm): `node_modules/eligian` is a symlink. `fs` reads follow it, and the path passed to `node` is the symlink path, which Node resolves. The FR-003 watcher's base is that symlink itself, which VS Code follows ("unless the path to watch itself is a symbolic link", `index.d.ts` `createFileSystemWatcher` doc).
- **An install in a sub-folder** (monorepo: `packages/talk/node_modules/eligian`): only workspace-folder roots are checked. The README says to open that folder or use `.vscode/mcp.json`.
- **A version change while a server runs**: the `version` field changes, so VS Code prompts to refresh the tools (`index.d.ts` doc of `version`). `npm uninstall eligian` removes the definition (FR-003).
- **Multi-root**: one definition per qualifying folder. Each server's root is its folder (`cwd`), and the server's path policy (§2) keeps tool paths under that folder's root.
- **Concurrency on the shared Langium services**: unchanged. Resource reads touch only the knowledge cache (`loadKnowledge`), not the compiler lock (`compiler-lock.ts`), so they never wait behind a `check`. Parallel `resources/read` calls share the one cached `Knowledge` per directory.
- **stdout purity**: resources and prompts run in the same server process under the existing redirect (`stdio.ts`). The missing-docs line (FR-023) goes to stderr. SC-013 re-runs the spawn test with the new methods.
- **Missing files**: no `index.json` (FR-023); a resource id in the index whose body file is missing (a broken docs build), where `resources/read` returns a JSON-RPC error naming the id, and the server keeps running; a missing `.vscode` directory (no FR-004 effect); a missing `.eligian` directory (FR-018 creates it, with its self-ignoring `.gitignore`, FR-037); the entry deleted while `dev` runs (the build fails, and the file holds the `build-error`).
- **Stale caches**: `loadKnowledge` caches per docs directory for the process lifetime. A newer `eligian` install means a new process (VS Code restarts the server on a `version` change), so a stale docs cache inside one process cannot outlive an install. In `dev`, a report from the previous page (posted during unload, with `keepalive`) carries the old `buildId` and is dropped (FR-014). The map is that of the current reload-build: a CSS-only build keeps it, because the running page keeps its action ids (FR-033). While a build is failing, `engine-error` reports cannot come from a current page, so they are dropped.
- **Cold start time**: the resource list is built from `index.json` only (40 KB), and the bodies load lazily. The `initialize` time stays under 3 s (`package-bin.spec.ts`, SC-013). Extension activation does no network and no process spawn: only `fs.stat`/`readFile` of up to two small files per folder, and `findFiles` with a limit of 1, run after `activate` returns, so they do not block activation.
- **Errors before the dev client hooks in**: the hook (FR-015) closes the gap for engine errors. A failure in `createEngine` itself (an invalid config) rejects `ready`, the bundle's `ready.catch(console.error)` (`runtime-bundler.ts:253`) logs it, and FR-016 (c) forwards it as a `console-error`.
- **Listener actions** (DOMEventListenerController, KeyboardController) are not timeline actions, so Eligius does not emit `error` for them (`IEngineActionError` doc). Their failures reach the console or `unhandledrejection` and are forwarded without a location (FR-017).
- **Double reporting**: once the client subscribes to `error`, Eligius stops logging, and the client logs it itself (FR-016 (b)) without posting it as a `console-error`. One engine error therefore gives exactly one report (SC-009 (2)).
- **Hostile pages**: the runtime route accepts only same-origin or origin-less requests (FR-014). Bodies are capped. The file is capped at 100 entries. The route never executes or `eval`s anything from the body.
- **The preview**: unaffected (non-goal). It does not load `DEV_CLIENT_SCRIPT`, and never sets `__eligianDevHooks`.

## Interpretations (roadmap tensions resolved here; input for the clarify scan)

- **I-1 (`eligian.mcp.command`).** The roadmap gives only the setting's name. This spec reads it as the program that runs the workspace-local `cli.js`, with default `node` (FR-007), which mirrors the `command` field of `McpStdioServerDefinition` and of `.vscode/mcp.json`. That keeps decision 2: the server is always the folder's own install. Alternative: a full command line that replaces the install (for example, a global `eligian`). That would bypass decision 2's version gate and the "workspace-local" requirement.
- **I-2 (`.vscode/mcp.json` precedence).** "`.vscode\mcp.json` still works" could also mean only "is not broken". This spec makes a user-configured server win (Q4): the `eligian` key or an Eligian cli.js / npx stdio server in the folder's `.vscode/mcp.json` (FR-004), or in the workspace-level `mcp` configuration (FR-034), so that a user with both does not get every tool twice. The user-profile file is out of scope. Alternative: always provide, and leave both servers running.
- **I-3 (Cursor exclusivity).** When `vscode.cursor.mcp.registerServer` exists, the extension uses it instead of the `lm` provider, so that Cursor does not register the server twice if it also implements the `lm` API. The roadmap's "Cursor branch … when present" supports either reading.
- **I-4 (install prompt mechanics).** The roadmap says only "an install prompt". This spec shows it from activation and the watchers (never from `provideMcpServerDefinitions`, whose contract forbids UI), once per activation, with **Don't Ask Again**, and runs a package manager in a terminal (FR-008), found by walking up to the nearest lockfile or `packageManager` field (FR-035) and choosing `add` or the plain `install` by the folder's declared range (FR-036). The four package managers are an interpretation; this repo's "pnpm only" rule governs this repo, not users' projects. Decision 2's "otherwise" is read as "otherwise, in a folder that is an Eligian project": the prompt needs `.eligian` files or an existing `node_modules/eligian` that fails the gate (FR-008), so a folder with `eligian` 1.0.x and no `.eligian` file yet is prompted, and an unrelated folder (which `workspaceContains:**/*.eligian` would not activate on anyway, but a multi-root sibling would) is not. Alternatives: prompt only for folders with `.eligian` files (narrower than "otherwise"), or every trusted folder (noise in non-Eligian folders). With several failing folders, one notification per activation in total names the first; alternative: one notification per failing folder.
- **I-5 (activation).** FR-005 adds `workspaceContains` events so that registration does not wait for an `.eligian` editor. The MCP-specific event is [UNVERIFIED] and is added only if confirmed.
- **I-6 (static resources, not a template).** `effect/ai` matches template parameters per path segment (Verification record), and 101 of the 140 ids contain `/`. So each chunk is a static resource with its id verbatim in the URI (`eligian://docs/operation/addClass`). This also puts every chunk in `resources/list`, which is what @-mention lists. Alternative: two templates (`{id}` and `{group}/{name}`), which @-mention clients may not list.
- **I-7 (prompt parameters and content).** The roadmap names only the prompt. This spec gives it one required argument, `idea`, and the §5 workflow as content (FR-025). Alternative: also a `template` argument (`blank|chapters|video|library`), which would duplicate the choice `decisions.md` teaches.
- **I-8 (`dev-errors.json` shape, location, reset).** The roadmap names the file only. Shape, cap, merge and reset on rebuild are this spec's (FR-018). The file sits under the entry's directory, the directory `dev` watches and serves from (`root = path.dirname(input)`, `dev-server.ts:82`). `dev` writes `.eligian/.gitignore` containing `*` when it creates the directory (FR-037, Q5); the user's root `.gitignore` is not edited, and the starters are unchanged.
- **I-9 (instructions unchanged).** No new tool, so no Phase 4 instructions variant. The new `dev` behaviour is taught by `verification-ladder` (FR-030) and the prompt (FR-025).
- **I-10 (test location).** The roadmap path `packages\extension\src\__tests__\mcp-provider.spec.ts` does not exist as a directory. The spec goes to `packages/extension/src/extension/__tests__/`, beside the other 27 specs.
- **I-11 (the bundle hook).** `runtime-bundler.ts` is not in the roadmap's touched files. Without the hook, errors at position 0 (the `on enter` of the entry timeline) cannot be located, because the engine is private to the bundle and starts before `ready` resolves (Verification record). The hook is a no-op without the dev client.
- **I-12 (map from the same build).** `BundleResult` gains `map`. Compiling a second time for the map would give different ids (`crypto.randomUUID()` per compile), so the map must come from the bundled compile.
