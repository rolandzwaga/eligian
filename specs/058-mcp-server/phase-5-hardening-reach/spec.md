## Overview

Phases 0–4 shipped `eligian mcp` with eight tools, the curriculum, the review pass, smoke scenarios and determinism, provenance, the eval harness, VS Code registration and `dev` runtime feedback. Phase 5 is the trailing hardening-and-reach phase, and the roadmap gives it three bullets:

1. **Promote review checks to DSL validators** where the evals showed they matter and an editor squiggle is worth it. Each promotion is its own mini-spec. `runtime-state-pitfalls.md` moves each promoted code from "caught by check" to "caught in the editor".
2. **Reach**:
   - an MCP registry entry: `"mcpName": "io.github.rolandzwaga/eligian"`, a `server.json`, and a `mcp-publisher publish` step after `npm publish` in `publish-cli.yml`, per §2 "MCP registry";
   - an optional Claude Code plugin (`.claude-plugin/`) and its Codex/Cursor equivalents.
3. **Server recycling tuned from the soak test**: the interval N (100 today) is chosen from measurements of a realistic tool mix, not only repeated `eligian_check` calls on one fixture.

The exit is `check:examples` green, the registry entry visible, and an eval re-run without regression. The exit stays open until the user has run Phase 3's full evals (the promotion evidence) and Phase 5's own phase-exit run (SC-003).

## User scenarios and testing

### User story 1: the editor shows what `check` would have said (P1)

An author writes a timeline whose `on enter` adds a click listener and whose `on leave` does not remove it, or a media timeline whose `from` file does not exist. Today only `eligian check` / `eligian_check` reports it, after a save and a terminal run. After promotion, the editor squiggles it while they type, with the same code and the same message. Where the CLI offers a quick fix (today only `controller-imbalance`, Verification record), the editor offers the same edit as a code action.

Acceptance (per promoted code `<c>`):
1. Given a fixture that triggers `<c>`, the language server reports exactly one warning with code `<c>` at the same range `eligian check` reports.
2. Given the same fixture, `eligian check` and `eligian_check` report `<c>` exactly once. It is not reported twice, once as a validator and once as a review finding.
3. Given the clean counterpart fixture, there is no `<c>` anywhere.
4. If `<c>` carries a CLI quick fix, the editor's code action for that diagnostic applies the same edit (SC-019).

### User story 2: an agent finds the server in the MCP registry (P2)

A user browses the MCP registry (or a client that reads it) for "eligian" and finds `io.github.rolandzwaga/eligian`, which starts with `npx -y eligian@<version> mcp`.

Acceptance:
1. After the user runs *Publish CLI* on `main` for a version that carries `mcpName`, `GET https://registry.modelcontextprotocol.io/v0/servers?search=io.github.rolandzwaga/eligian` returns that server at that version.

### User story 3: one-command install in Claude Code (P3)

A Claude Code user runs `/plugin marketplace add rolandzwaga/eligian` and `/plugin install eligian@eligian`. In every project they then have the `eligian` MCP server, with no `.mcp.json`. Cursor users keep the Phase 4 extension's Cursor branch (`server-definition-provider.ts:198`, `cursorMcpApi`); there are no Cursor or Codex plugin files (FR-017, FR-018).

### User story 4: a long agent session does not slow down or bloat the server (P2)

An agent session makes hundreds of mixed calls (`check`, `project`, `compile`, `fmt`, `operations` with `path`). The server's heap stays bounded, and the call right after a recycle is not noticeably slower than the others.

### D. Recycling tuned from the soak test (§7 bullet 2; §2 "Memory and staleness")

- **FR-022** A measurement script (`packages/cli/scripts/measure-recycle.ts`, run with `tsx --expose-gc`; outside tsconfig, as the generator is) MUST drive the in-process server (`startInMemoryServer`, `mcp-test-client.ts:123`) through a **tool mix** on a realistic project. The default project is `examples/eligian-tour` (several timelines, libraries, CSS, layout, locales, a host module). The mix is the 5-tool sequence `M = [eligian_check, eligian_project, eligian_compile (view: 'summary'), eligian_fmt (write: false), eligian_operations with path]`. On `eligian-tour` each of these calls is exactly one lock section (Verification record), so sections = calls there; the script MUST count sections through the lock's `onAcquire` hook and recycles through `onRecycle` (`compilerLockLayer(hooks, { recycleAfter: N })`, the production `makeCompilerLock`), and MUST stop with an error if sections ≠ calls (another `--project` with several programs is then measured in sections, not calls). **Rotation:** every N in the candidate set is a multiple of 5, so a fixed cycle would always put the same tool right after a recycle. The call with 0-based index `i` therefore uses `M[(i + r(i)) mod 5]`, where `r(i)` is the number of recycles completed before call `i`: after each recycle the cycle advances by one tool, so the post-recycle call varies across tools.

  It runs 500 calls for each N in {25, 50, 100, 200}, plus one 500-call run with recycling off (`recycleAfter` larger than the call count) as the **reference** row "never". For each run it records:
  - heapUsed after a forced GC before the first call and after the last; *(ruling 2026-11-06, build T020: "before" is taken after the **warm-up round**, the first |M| = 5 calls (one per tool), which still count toward the 500; from a cold start every row grew 49–74 MB, about 37 MB of it the one-time load of the compiler, docs, registry and formatter, so the cold reading measured start-up, not session growth; the cold-start table is kept as `baseline/recycle-measurements-cold.txt`)*
  - the number of sections and of recycles;
  - each call's tool and latency (client-side, from request to response), in the raw output;
  - per tool `t`: `base(t)` = the median latency of `t`'s calls that neither triggered a recycle nor immediately follow one;
  - per recycle `k`: `post(k)` = latency of the first call after recycle `k` ÷ `base(tool of that call)`, and `trig(k)` = latency of the call whose section triggered recycle `k` (it waits for the recycle inside the permit, `compiler-lock.ts:83-99`) ÷ `base(tool of that call)`;
  - the medians `median_k post(k)` and `median_k trig(k)`, and the overall median and p95 latency.

  It also runs an **`eligian_fmt`-only** run: 500 sequential `eligian_fmt` calls (`write: false`) on the same project, with recycling on at N = 100, recording heapUsed after a forced GC after every 100 calls (FR-025).

  The output goes to `baseline/recycle-measurements.txt`. *(§7: "tuned from the soak test")*
- **FR-023** `RECYCLE_AFTER` MUST be set from FR-022's data by this rule, applied to the four numeric candidates {25, 50, 100, 200} only: the largest N whose 500-call heap growth stays at or under 25 MB (the existing `CEILING`, `mcp-soak.spec.ts:22`), **and** whose `median_k post(k)` ≤ 3 **and** `median_k trig(k)` ≤ 3 (FR-022 definitions). "never" is a reference row, not a candidate: without recycling the heap grows with session length (Phase 1: 0.047 MB per call, Verification record), and a 500-call window cannot show that it stays bounded in a longer session. If no N meets all three, N is the candidate with the lowest heap growth and the plan records why. The chosen N and the table MUST be recorded in `baseline/recycle-measurements.txt` and in the `RECYCLE_AFTER` doc comment.
- **FR-024** `mcp-soak.spec.ts` MUST gain a mixed-tool case with the FR-022 mix and rotation, on `examples/eligian-tour` (copied to a temp dir) or another one-program fixture named in the plan, at the chosen N, for at least 2 × N calls (so at least 2 recycles), under the 25 MB ceiling *(measured from after the warm-up round, as FR-022; ruling 2026-11-06)*, still in the `cli-soak` project. ## Edge cases

- **E-1 Windows and Linux paths.** A promoted media check resolves `from` paths through `resolveImportRelativePath` (`timeline-review.ts`). In the editor, the document URI is a `file:///f:/…` URI whose `fsPath` has backslashes on Windows. The validator MUST take the path from `document.uri.fsPath`, the same way `lintDocument` does (`eligius-lint.ts:42`), and its tests MUST cover a Windows-shaped and a POSIX-shaped path through the injectable `exists` option of `timelineFindings`. The registry and plugin files use forward slashes and no absolute paths.
- **E-2 Concurrency on the shared Langium services.** A promoted validator runs inside Langium's document builder. In the MCP server that happens under the compiler lock already, because `checkFiles` runs validation in the locked section. The validator MUST NOT call `getOrCreateServices()` itself: it gets its services from the validator's injection. The I-2 channel in the language server runs on the language server's own services, not the CLI singleton. The FR-022 script and the mixed soak MUST issue calls sequentially through the in-process server and the lock built by the production `makeCompilerLock` (through `compilerLockLayer(hooks, { recycleAfter })`, which adds only the counting hooks), never by calling `checkFiles` directly.
- **E-3 Stdout purity.** The `mcp-publisher` and plugin work adds no output to `eligian mcp`. The FR-012 handshake spec reads stdout as protocol frames only (the existing `spawnServer` contract). A promoted validator MUST NOT log with `console.log`.
- **E-4 Missing files.** A media validator in the editor sees files appear and disappear without a re-validation trigger, because Langium re-validates on document change, not on an unrelated file's creation. The mini-spec MUST state whether a stale squiggle after `media/intro.mp4` is created is acceptable until the next edit (the default) or needs a file watcher. `check` is always fresh.
- **E-5 npm propagation.** Right after `npm publish`, `npm view eligian@V mcpName` may 404 for some seconds. The registry's ownership check then fails, which FR-014's bounded retry covers. If it is still failing after the retries, the job fails with npm already published. Re-running only the registry step must be possible: the `registry_only` input (FR-013d).
- **E-6 Version skew.** `server.json` `version` must equal the npm version being published. A bump of `package.json` without `server.json` fails SC-004 in CI, before `publish-cli.yml` ever runs. The registry rejects re-publishing the same version (**[UNVERIFIED]**: the plan checks the registry docs). So a failed npm publish of V followed by a re-run must not leave the registry at V with npm at V-1, which the step order guarantees.
- **E-7 Stale caches.** Recycling drops the Langium singleton. A promoted validator that caches per document (as `parameter-roles` does) MUST key the cache by the document, or clear it on `resetServices()`, so a recycled server does not use AST nodes from the old services. The staleness specs (`mcp-staleness.spec.ts`, including the recycle variants) MUST stay green.
- **E-8 `npx` on Windows in the plugin file.** Claude Code starts plain `npx` (`agents.ts:44-45` comment, `:46` branch), so the one Claude Code plugin file is correct on every OS (FR-019). Cursor, which needs `cmd /c npx` on native Windows, has no plugin file (FR-017) and is served by the extension and `eligian agents setup`.
- **E-9 Duplicate servers.** A project made by `eligian init` has `.mcp.json` with server `eligian`, and the user may also have the plugin installed. Whether Claude Code lists the tools twice, under the project server and under the plugin's namespaced server, is **[UNVERIFIED]**. The README states the outcome measured in SC-009, and the plan decides whether the plugin's server key differs or the README tells the user to pick one (FR-021).
- **E-10 Cold start.** The plugin and registry launch forms that use `npx -y` add an npm cache check (and on first use a download) before `initialize`. The Codex 10 s startup limit (§2 "Startup budget", **[UNVERIFIED]** there) applies to the registry entry's `npx` launch. SC-017 keeps the in-process start < 3 s, and the README notes that the first `npx` start downloads the package.
- **E-11 No eval data.** If Phase 3's full runs do not exist when the plan runs, the build follows FR-001b: the promotion tasks stay blocked. SC-003's comparisons with a baseline ((a)–(d)) are then PARTIAL ("no baseline"), its §6.3 check (e) still applies to this phase's own run, and no promotion is built (FR-001b): the compliance table lists the promotion rows as blocked.
- **E-12 Recycle during a promoted validator's run.** The recycle runs inside the permit after a section completes (`compiler-lock.ts:11-14`), so no validation is in flight. The I-2 channel in the language server is not affected by the CLI's recycle.

## Interpretations (roadmap tensions resolved here; input for the clarify scan)

- **I-1 "server process recycling".** §2 describes recycling the *Langium services* after N compiler calls, and Phase 3 built that in the lock. A stdio server cannot restart its own process without the client seeing a disconnect. Phase 5 therefore tunes the in-process service recycle (FR-026).
- **I-2 "DSL validators" for config-based checks.** Three of the review checks read the compiled config. A Langium validator sees only the AST. The language server already compiles every clean program in memory 200 ms after validation, for the Eligius lint, and publishes the findings as editor diagnostics. Sending a promoted config-based check through that channel gives the squiggle the roadmap asks for ("where an IDE squiggle is worth it") without a second compile. Decided (clarification Q2): it counts, with `DiagnosticSource` `'config'` (FR-003, FR-005c).
- **I-3 `--no-review` after promotion.** A promoted code follows the validator rule, and neither the review switch nor the lint switches cover it (FR-006). This keeps one rule: validator warnings are always on. For a config-based code that needs new wiring, because today both the editor and `check` gate the compiled-config findings behind the lint/review switches (FR-005a). It changes behaviour for anyone who used `--no-review` (or `eligiusLint: false`) to silence a promoted code, and the CHANGELOG says so.
- **I-4 Registry version.** The registry checks `mcpName` in the published package. 1.1.0 is unpublished and already carries the `mcp` subcommand, so adding `mcpName` to 1.1.0 needs no version bump. The first *Publish CLI* run of 1.1.0 publishes npm and the registry together.
- **I-5 Plugin launch form vs decision 2.** Decision 2 (the extension) and §2 (generated configs prefer the project-local `node …/cli.js`) both want the project's own compiler version. A user-scope plugin has no project at install time. Decided (clarification Q4): the `npx` form, `npx -y eligian@^1.1 mcp`, with the README keeping `eligian init` / `agents setup` as the per-project pinned route (FR-019, FR-021).
- **I-6 Baseline for "without regression".** The roadmap gives no baseline or tolerance, but it does fix the shape of a phase-exit run: arms A1 and A0, 3 runs per case, Sonnet-class, plus one Opus-class run (§6.4, decision 9), judged by the §6.3 exit rule. SC-003 therefore runs a full phase-exit run by default, compares A1 with Phase 3's final full run (`evals.md`) on the metrics the Phase 3 exit gates on, applies §6.3 to A1 vs A0, and fixes (clarification Q5) the baseline as Phase 3's final full run, the tolerance as 5 %, the run count as 3 per case, and rows (a)–(d) as PARTIAL when the baseline does not exist.
