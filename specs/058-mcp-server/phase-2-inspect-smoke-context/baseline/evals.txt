## Defects found

### three-chapters (both models): case defect in the scenario, step 3
The scenario (evals/mcp/cases/three-chapters.scenario.json:23 and :27) asserts the exact controller list
["DOMEventListenerController"] on #to-problem after the return to the hub. Both agents localized the hub
button labels as well (sonnet: `label("#to-problem", "hub.problem")`, an action that adds LabelController;
opus: `with "#to-problem" { addController("LabelController", "hub.problem") }`). The prompt does not
forbid that, so #to-problem legitimately carries ["LabelController", "DOMEventListenerController"]. The programs
are otherwise right: check 0/0, fmt clean, their own smoke scenarios ok, and the gate's case checks
(4 timelines, a __nav__* action, languages, LabelController, on enter / on leave) report nothing.
None of the three categories fits: it is an over-strict case assertion (the intent is the listener balance:
DOMEventListenerController present once, none on #back-problem). A re-run needs a case change
(assert that DOMEventListenerController is contained, or say in the prompt that the hub buttons are not localized).

### three-chapters (sonnet): compiler gap, the 3 rounds (step 5 rounds)
Round 1 called a helper `action unclick(selector: string) [ selectElement(selector)
removeControllerFromElement("DOMEventListenerController") ]` from on leave. `controller-imbalance` reported
a false positive in all four timelines, e.g.
  "Timeline \"Hub\": on leave does not remove controllers that on enter adds: DOMEventListenerController on \"#lang-en\", ...;
   on leave removes controllers that on enter does not add: DOMEventListenerController on \"undefined\", ..."
Reproduced on the agent's first main.eligian (extracted from claude-transcript.json) with the repo CLI
(`node packages/cli/bin/cli.js check main.eligian`: "1 file, 0 errors, 4 warnings").
Cause: in the compiled action the `selectElement` has operationData null (the parameter reaches it implicitly,
by name, through the operation data), and the walker sets the selection only from the operation's own `selector`:
packages/language/src/compiler/controller-balance.ts:101-103
  case 'selectElement':
    selector = resolveOperationData(own.selector, data);
so every selection made through a parameter named `selector` is "undefined". The same bug hides real
imbalances: the agent's `label` / `unlabel` helpers balance only because both sides are "undefined LabelController".
Fix direction: fall back to `data.selector` when `own.selector` is absent. The agent then spent rounds 2-3 on
shell edits that the harness refused (python not installed; sed needing approval) before it rewrote the file
with the removals inlined.

### three-chapters (both models): tool ergonomics, step 5 tokens-from-tools
91,440 (sonnet) and 81,435 (opus) chars against 80,000. The largest returns in the sonnet run: the first
eligian_docs call (storyboard, decisions, project-layout, syntax-cheatsheet, operations-index, detail: 43,288 chars),
the agent's own eligian_smoke scenario (19,024 chars) and 3 identical 4,617-char check results (the false
positive above). Passing cases sit close to the budget too (sonnet keyboard-deck 76,913, opus library-reuse 76,825,
opus title-card 74,576): the docs bodies dominate. Fixing the false positive removes about 9k chars from the sonnet
run; the opus run needs leaner docs or smoke results.

### staggered-list (both models): curriculum gap
Both agents fetched the stagger chunks (example/stagger-action, example/stagger-inline) and wrote six plain
ranges instead (`at 0s..6s target "#card-1" [ addClass("is-visible") ] [ removeClass("is-visible") ]` ...
`at 2s..6s target "#card-6" ...`), which is check 0/0, fmt clean and passes the case's scenario. The prompt says
every card stays visible once it has appeared, i.e. items of unequal length (0..6, 0.4..6, ..., 2..6); both taught
stagger forms are items of one fixed length whose end block undoes the start (`for 1.5s`;
`for 2s [ ... ] [ ... removeClass("lit") ]`). The stagger form that fits the prompt, a start block only plus the
removal in on leave, is not taught, and without the on leave it fails the gate's check step: probed with the repo CLI,
`stagger 400ms [the 6 cards] at 0s for 4s [ selectElement(@@item) addClass("is-visible") ]` gives 6
`class-never-removed` warnings ("remove it in the end block, a later range or on leave"), exit 1 under
--max-warnings 0. A re-run needs a curriculum change (an example of a "reveal and stay" stagger whose classes
are removed in on leave) or a prompt that names `stagger`.
