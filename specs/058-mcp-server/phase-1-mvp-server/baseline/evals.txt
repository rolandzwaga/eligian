## Defects found

### fix-dataflow: compiler gap (check is clean, the runtime fails)
The agent's final program passes `eligian check main.eligian --max-warnings 0 --selector-not-in-layout ids`
(re-run in the eval dir: "1 file, 0 errors, 0 warnings", exit 0), but `eligian smoke main.eligian --strict` fails:
  error  start operation selectElement (in reveal): selectElement: selector is either empty or not defined.
         main.eligian:15:3 — 'main' at 3s
The agent's `reveal`:
  action reveal(selector, className) [
    selectElement(selector)
    addClass("visible")
    clearOperationData()
    selectElement(selector)   // added by the agent
    addClass(className)
  ]
Cause: `clearOperationData()` (no property list) wipes the action's parameters (`selector`, `className`) and the
`__eligian_param_*` saves from the operation data. The compiled `reveal` (out/config.json) is:
  setOperationData {__eligian_param_selector}, selectElement, setOperationData {selector <- save},
  setOperationData {__eligian_param_className}, addClass, setOperationData {className <- save},
  clearOperationData, selectElement, addClass
so nothing restores them after the clear. Neither side models it:
  - the dataflow validator: `clearOperationData` -> `state.clearAll(operation)` (packages/language/src/dataflow/operation-dataflow.ts:750-753)
    removes only tracked properties (operation-data-tracker.ts:148-151); action parameters are not among them, so a
    parameter read after the clear gets no `erased-property-access` (the start state reports it only for 'selectedElement', 14:3);
  - `preserveErasedParameters` (packages/language/src/compiler/transformers/erased-parameters.ts) saves/restores only
    parameters named like an `@erased` property (`erasedBy`), not the ones `clearOperationData` removes.
The start state already carries the latent runtime error (`addClass(className)` after the clear), which the check never
reports, so the agent cannot find it with `eligian_check` alone. Classification: compiler gap. A re-run needs a fix
(flag parameter use after `clearOperationData`, or preserve parameters across it), not a curriculum change.

### fix-selectors: tool ergonomics (budget overrun by one round)
Diagnostics per eligian_check call:

  2: controller-imbalance 16, class-never-removed 21 and 22 (0 errors, 3 warnings)

Two causes, either one alone keeps the run inside the budget of 2:

     call 1 showed none of them though ProgressbarController's imbalance and both addClass calls
     are in the start state. The agent fixed what it was shown, then met three new warnings.
  b) Round 3 was wasted: the agent tried to rewrite main.eligian with a Bash heredoc, which Claude Code refused
     ("Contains brace with quote character (expansion obfuscation)"; ALLOWED_TOOLS in evals/mcp/run.ts allows only
     `Bash(node *)` and `Bash(npx eligian*)`), then ran eligian_check on the unchanged file before switching to Write.
The final program is correct and complete (check 0/0 via the CLI command of the prompt, exit 0; the agent applied the
controller-imbalance quickFix verbatim and made the actions endable to remove the classes).
Classification: tool ergonomics (review deferred behind errors; the eval's Bash allowlist). No compiler or curriculum gap seen.
